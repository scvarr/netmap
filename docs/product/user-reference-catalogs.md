# Пользовательские справочники и границы L1

## Статус и продуктовая цель

**Согласованное продуктовое направление; implementation contract OPEN.**
Новые возможности этим документом не объявляются IMPLEMENTED.

До перехода к L2 пользователь должен иметь возможность достоверно описать
собственную физическую сеть без изменения application code для добавления
типов оборудования, портов или кабелей. Порядок [roadmap 11.3](../plans/11-03-pre-l2-product-completion.md)
сохраняется: L1 semantic completion -> pre-L2 productization ->
`L1 PRODUCT COMPLETE` -> semantic L2 -> L3. Ранний переход к L2 не предлагается.
Phase C остаётся **PAUSED**, HV-01 — **NOT PASSED**.

## Продуктовая поверхность «Справочники»

Отдельный раздел «Справочники» позволяет создавать собственные значения,
выбирать и повторно использовать существующие, переименовывать записи и
безопасно управлять удалением используемых записей. Создание нового значения
доступно непосредственно из соответствующей формы: предварительный переход
в раздел «Справочники» не обязателен.

Начальные области применения:

- типы оборудования;
- типы Location;
- пользовательские типы портов;
- типы кабелей;
- виды разъёмов;
- значения совместимости модулей.

Это не закрытая taxonomy и не точный scope первой реализации. Дополнительные
справочники вводятся по подтверждённой пользовательской необходимости.
Открытые значения не ограничиваются закрытыми enum. Универсальный конструктор
произвольных полей и rule engine не входят в это направление.

## Четыре разных класса информации

| Класс | Граница |
| --- | --- |
| Канонические сущности и отношения | `PhysicalObject`, `Location`, `ConnectionPoint`, `NetworkInterface`, `Connection`, `ConnectionMember` и явные отношения описывают факты сети. |
| Пользовательские классификации и определения | Типы и описательные характеристики помогают описывать сеть; они не создают отдельные канонические классы оборудования, портов или кабелей. |
| Фиксированные технические состояния приложения | Структурные варианты `CONNECTION_POINT` / `NETWORK_PORT`, lifecycle statuses, типы канонических отношений и другие программные состояния остаются контролируемыми контрактами, а не редактируемыми справочниками. |
| Производное read/presentation state | Отображаемые имена, счётчики, геометрия и другие проекции не становятся topology evidence. |

Запись справочника имеет стабильную идентичность, независимую от её
отображаемого имени. Переименование классификации не меняет идентичность
классифицированных сущностей и физическую топологию.

Классификация сама по себе не доказывает физическую совместимость,
поддерживаемую или согласованную текущую скорость, физическую связность либо
L2/L3 семантику. Отсутствие необязательной характеристики не является ошибкой
физической топологии. Connectivity задаётся каноническими фактами, а не
названием типа, Blueprint, Port Block или отображением на карте.

## Порты, шаблоны и Cable

`BaseTemplate` и `ModuleTemplate` должны в дальнейшем поддерживать
пользовательские характеристики портов. Это будущее расширение
[09.6](../architecture/blueprints/09-06-hardware-template-module-contract.md),
а не изменение уже реализованных контрактов этим docs milestone.

Не смешиваются форм-фактор SFP/SFP+/QSFP, физический разъём, среда передачи,
сетевая технология, номинальные capability и configured/observed state.
Пользовательский тип порта не заменяет структурный вариант endpoint.
Значение совместимости module/bay не доказывает совместимость физического
линка и не задаёт технологию endpoint; этот документ не меняет действующее
точное сопоставление значений module/bay из 09.6.

Тип кабеля — описательная классификация, а не шаблон генерации кабельного
имени. Существующая Cable naming-template library остаётся генератором label.
Сохраняется [Cable contract](../architecture/l1/01-01-02-cable.md): Cable —
optional domain entity ровно над одним Connection, без собственных endpoint
points, PhysicalObject inventory или Blueprint provenance. Справочник видов
разъёмов не вводит connector inventory.

`ConnectionPoint`, `NetworkInterface`, `Connection`, `ConnectionMember` и
`Cable` сохраняют независимые обязанности и стабильную идентичность.
Справочники не заменяют явный physical binding или member mapping.

Опубликованные ревизии остаются неизменяемыми. Семантика ссылок из immutable
revision на изменяемый справочник должна быть отдельно согласована **до
implementation contract**: здесь не выбирается live reference, snapshot или
иной механизм. Переименование либо удаление записи не даёт права переписывать
опубликованную ревизию или менять её смысл неявно.

## Отдельная граница cardinality

`C-CAP-01` остаётся самостоятельной confirmed gap. Cardinality и явные
`ConnectionMember` — свойства [канонической физической модели](../architecture/l1/01-01-01-connections.md),
не пользовательская классификация. Их реализация не смешивается со
справочниками и характеристиками SFP/кабелей; тип разъёма не определяет
cardinality автоматически. Это направление не закрывает C-CAP-01.

## Размещение в roadmap

Справочники — необходимая pre-L2 product capability без изменения порядка A–I:

- Phase D: минимально необходимые классификации портов/кабелей для
  достоверного L1, отдельным bounded scope от C-CAP-01.
- Phase E: единый UX справочников, включая выбор, повторное использование и
  создание значений непосредственно из форм.
- Phase F: привязка справочников к workspace/access после согласования
  соответствующих контрактов.

## OPEN перед реализацией

- Конкретная модель хранения справочников.
- Точный набор первой реализации.
- Семантика ссылок из immutable revisions на изменяемые записи.
- Правила удаления и обновления используемых значений, включая последствия
  для существующих ссылок и безопасный пользовательский workflow.
- Будущие правила технической совместимости.

Продуктовое требование безопасного управления используемыми значениями не
предрешает конкретную deletion/update policy. Workspace/access scope также
не фиксируется до соответствующих контрактов Phase F.
