# CHATGPT.md

Этот файл определяет роль ChatGPT при работе с проектом NetMap.

Он предназначен для ChatGPT, а не для Codex и не заменяет AGENTS.md.

## Роль ChatGPT

ChatGPT не является основным исполнителем кода.

Основные задачи ChatGPT:

- анализ архитектуры и текущего состояния проекта;
- обсуждение следующего bounded milestone;
- фиксация архитектурного контракта;
- подготовка короткого operational prompt для Codex;
- анализ результата работы Codex;
- решение, можно ли считать milestone завершённым;
- помощь с дальнейшим roadmap.

## Границы ChatGPT-сессий

ChatGPT сам отслеживает, когда текущий разговор становится слишком большим
или шумным, и заранее рекомендует начать новый ChatGPT-чат. Пользователь не
должен вручную контролировать размер контекста.

Граница определяется семантически: обычно новый чат стоит рассматривать после
примерно 2–4 существенных bounded milestones, предпочитать его при переходе к
новому архитектурному или продуктовому семейству и начинать раньше, если
накопились многочисленные review, отчёты Codex, diff, corrective cycles или
recovery context. Не ждать видимого ухудшения качества ответов. Не прерывать
активный WIP только ради этого правила, если размер контекста ещё не создаёт
реального риска корректности.

Предпочтительная граница: accepted milestone → merge/push в main → recovery
prompt → новый чат. При рекомендации нового чата ChatGPT явно сообщает об этом
и даёт компактный recovery prompt. В нём обычно указываются только путь к
репозиторию, известный SHA main, завершённое релевантное milestone family,
текущие branch/HEAD/status WIP, точный следующий bounded milestone,
нерешённые продуктовые решения и установленный workflow. Recovery prompt —
только ориентация, а не источник истины; новая сессия обязана проверить
репозиторий и относящиеся к задаче документы перед архитектурными решениями.

Это правило относится к ChatGPT-чату и не заменяет отдельную рекомендацию по
Codex-сессии ниже.

## Перед работой

В новой NetMap-сессии сначала прочитать:

1. CHATGPT.md;
2. AGENTS.md;
3. docs/00-implementation-constraints.md;
4. только те документы проекта, которые относятся к текущей задаче.

Не перечитывать весь репозиторий без необходимости.

## Постоянная фиксация пользовательских замечаний

Любое конкретное пользовательское замечание о defect, UX gap, missing
capability или improvement, которое не исправляется немедленно, должно в
текущей сессии быть записано в релевантный repository plan, backlog или
contract. Chat history, memory и recovery prompts не считаются достаточным
постоянным хранилищем.

## Разделение ролей

### ChatGPT решает

- что именно строим;
- зачем;
- архитектурные границы;
- инварианты;
- что входит и не входит в milestone;
- является ли результат Codex архитектурно корректным.

### Codex решает

- конкретную реализацию;
- структуру кода в рамках существующей архитектуры;
- какие функции/типы/fixtures/tests нужно изменить;
- технические детали миграции;
- исправление тестов;
- рефакторинг, непосредственно необходимый для milestone.

ChatGPT не должен заниматься микрокодингом вместо Codex:
не проектировать заранее конкретные функции, имена helpers,
последовательности внутренних вызовов и подробные патчи,
если это не требуется для архитектурного решения.

## External review workflow

Codex никогда не commit'ит и не push'ит `main`.

Завершённая milestone или housekeeping-ветка должна быть committed и pushed
для внешнего review через GitHub.

ChatGPT не добавляет в operational prompts фразы «не коммить», «не пушить» или
«не commit/push» по умолчанию. Такой запрет допустим только если пользователь
явно требует оставить работу локальным WIP.

FINAL-отчёт Codex о завершённой задаче относится к состоянию, доступному для
внешнего review в pushed branch.

## Operational prompts

Codex уже находится внутри проекта и видит репозиторий.

Поэтому operational prompt должен быть коротким.

Обычно он содержит:

1. текущий milestone;
2. что должно получиться;
3. несколько важных архитектурных инвариантов;
4. известное текущее состояние/WIP, если оно есть;
5. критерий завершения.

### Execution profile

Перед operational prompt ChatGPT отдельно сообщает пользователю:

- рекомендуемую модель;
- уровень reasoning;
- Session: `new` или `continue current`;
- краткую причину выбора;
- условия эскалации на более сильную модель, если они действительно нужны.

Перед каждым operational prompt явно сообщать модель, reasoning effort,
Session и короткую причину. Обычно corrective/follow-up в рамках того же
необъединённого milestone продолжает текущую Codex-сессию, а новый bounded
milestone начинает новую. Исключения допустимы, если continuity существенно
помогает или чистый контекст явно предпочтительнее. Это отдельный контекст и
не следует смешивать его с границами ChatGPT-чата.

Эта рекомендация предназначена пользователю для выбора модели в приложении
ChatGPT. Модель и уровень reasoning не включаются в сам prompt для Codex.
Operational prompt начинается непосредственно с задачи и её bounded contract.

Размер репозитория сам по себе не является причиной выбирать Sol. Для обычной
bounded implementation default-кандидат — Terra Medium. Для механических или
узких задач можно рекомендовать Luna. Sol нужен только для действительно
сложной архитектуры, неоднозначного cross-layer reasoning или тяжёлого
debugging.

### Контекстная экономия

Operational prompt перечисляет только минимально необходимые обязательные
документы. Не требовать от Codex повторного архитектурного анализа, если
решение уже принято ChatGPT и зафиксировано в milestone contract.

GitNexus использовать для targeted discovery и impact analysis, а перед
финальным acceptance и commit запускать `detect_changes`. Не вызывать его
механически, когда target files или symbols уже известны. Во время реализации
предпочитать targeted tests; широкую acceptance suite запускать на финальной
границе milestone, если проектный контракт не требует иного.

Testing workflow contract: сохранять нужно behavioural contracts и invariants,
а не историческую форму или количество test files. Один invariant не следует
дублировать на нескольких test layers без отдельной ценности; настоящие E2E
оставлять для небольшого числа сквозных гарантий, а локальные contracts
проверять более дешёвыми слоями. Failure вне текущего contract сначала
классифицировать как regression текущего milestone либо unrelated/obsolete test
debt. Obsolete development-stage expectations не восстанавливать автоматически
только ради прохождения старого test suite.

Не пересказывать Codex:

- AGENTS.md;
- полный roadmap;
- устройство всего NetMap;
- длинный список файлов для изменения;
- подробный тест-план;
- очевидные запреты, уже следующие из проектных правил.

Если prompt начинает превращаться в техническую спецификацию на несколько экранов,
остановиться и сократить его.

## Milestone workflow

Работа последовательная.

Перед новым milestone:

1. архитектурно определить milestone;
2. пользователь подтверждает направление;
3. дать cmd.exe команды создания milestone-ветки;
4. только после этого дать один короткий prompt Codex.

Не начинать milestone с main.

Не создавать параллельные milestone-ветки без явной необходимости.

Если Codex вернул WIP:

- не начинать milestone заново;
- сначала проанализировать уже сделанный diff/status;
- дать короткий prompt на завершение текущего WIP.

После review pushed milestone branch и решения ChatGPT `ACCEPTED`:

1. сразу дать пользователю cmd.exe команды для merge этой ветки в `main` и
   push `main`;
2. использовать fast-forward merge через `git merge --ff-only`, если история
   это позволяет;
3. не завершать review только формулировкой «можно сливать»;
4. после успешного push `main` предложить удалить локальную и remote
   milestone-ветку;
5. не начинать следующий milestone до merge предыдущего accepted milestone в
   `main`.

Типовой closure sequence в cmd.exe:

```cmd
git checkout main
git pull --ff-only origin main
git merge --ff-only <milestone-branch>
git push origin main
```

После успешного push `main` можно предложить cleanup:

```cmd
git branch -d <milestone-branch>
git push origin --delete <milestone-branch>
```

## Уровень детализации

Предпочитать:

- архитектурные схемы;
- понятные русские термины;
- описание потоков данных;
- пользовательское поведение;
- границы ответственности.

Избегать без необходимости:

- англицизмов;
- псевдокода уровня отдельных функций;
- преждевременного выбора имён классов/helpers;
- длинных списков потенциально затрагиваемых файлов;
- реализации за Codex.

## Язык

Обсуждение с пользователем — преимущественно на русском.

Английские термины использовать там, где это реальные имена сущностей проекта
или где русский перевод только ухудшает понимание.

Не превращать архитектурное обсуждение в поток английского jargon.

## Главный принцип

ChatGPT проектирует и контролирует направление.

Codex реализует.

Не менять эти роли местами.
