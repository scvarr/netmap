# 01.6 NAT — packet transformation

## Статус

Согласованная базовая модель Network Address Translation как отдельной packet transformation.

Эта ветка определяет:

- NAT как преобразование `PacketState`;
- separation rule selection и packet mutation;
- ordered NAT policies/rules;
- reuse typed packet predicates;
- source/destination address и port transformations;
- identity NAT / NAT exemption;
- SNAT, DNAT, PAT, port forwarding и twice NAT как производные формы;
- deterministic и set-valued translation;
- dynamic pools;
- stateful NAT bindings;
- reverse traffic;
- configured/effective views;
- completeness и uncertainty;
- explainability before/after packet state;
- строгую границу с routing и security.

Полный порядок NAT относительно routing/security/L2 определяется [[03-04-packet-flow-trace|03.4 Packet Flow Trace]] через explicit `PacketProcessingPlan`.

Связанные заметки:

- [[01-05-security-policy|01.5 Security Policy]];
- [[01-04-l3|01.4 L3 — routing model]];
- [[01-07-policy-routing|01.7 Policy Routing]];
- [[03-03-l3-trace|03.3 L3 Trace]].

## Основной принцип

NAT отвечает на вопрос:

> Каким становится packet после применения translation semantics в данной точке processing?

Он не отвечает:

```text
разрешён ли packet firewall policy?
```

и не отвечает:

```text
какой route будет выбран?
```

Canonical decomposition:

```text
PacketState before
        |
        | NAT rule selection
        v
NATTransform
        |
        v
PacketState after / NATPacketConstraint
```

Routing/security stages получают тот `PacketState`, который существует в их реальной позиции pipeline.

## NAT не является Route

Route выбирает forwarding direction для **текущего** packet destination.

NAT может изменить:

```text
source_ip
destination_ip
source_port
destination_port
```

после чего route lookup может потребоваться для уже нового destination state.

Поэтому нельзя хранить:

```text
Route
    nat_to = ...
```

как универсальную semantics.

## NAT не является SecurityAction

Security:

```text
PERMIT / DROP / REJECT
```

решает, может ли packet продолжить processing.

NAT:

```text
PacketState A -> PacketState B
```

изменяет packet identity.

Даже если native vendor rule содержит:

```text
permit + source NAT
```

canonical adapter создаёт два semantic effects с общей provenance.

## Не фундаментальные SNAT/DNAT классы

Core не требует subclasses:

```text
SNATRule
DNATRule
PATRule
PortForwardRule
TwiceNATRule
```

Вместо этого rule применяет transformation к выбранным packet fields.

Например:

```text
change source_ip
    -> SNAT-like

change destination_ip
    -> DNAT-like

change destination_ip + destination_port
    -> port-forward-like

change source_ip + source_port
    -> PAT-like

change source and destination fields
    -> twice-NAT-like
```

Эти названия полезны UI и импорту, но не определяют core algorithm.

## PacketState

NAT использует тот же conceptual `PacketState`, что и Security.

Минимально:

```text
PacketState
    source_ip
    destination_ip
    ip_protocol
    source_port?
    destination_port?
```

NAT resolver никогда не должен молча использовать original packet, если current pipeline state уже был изменён предыдущей transformation.

## Packet lineage

Для explainability важно различать:

```text
original_packet_state
current_packet_state
```

Каждая transformation step создаёт новую immutable semantic version:

```text
P0 original
    |
NAT step N1
    v
P1 translated
    |
later processing
    v
...
```

Предыдущий state не переписывается.

Для exact result новая version является `PacketState`. Для `TRANSFORMED_CONSTRAINED` result представлен отдельным `NATPacketConstraint`, а не fake exact `PacketState`; constrained field не получает representative value.

Это позволяет ответить:

```text
какой destination видел DNAT rule?
какой destination видел firewall rule?
по какому destination выполнялся route lookup?
какой source ушёл на wire?
```

## NAT evaluation context

Кроме packet fields applicability может зависеть от local processing context.

Концептуально:

```text
NATEvaluationContext
    packet_state
    traffic_class
    routing_context_id?
    ingress_network_interface_id?
    egress_network_interface_id?
    ingress_l3_binding_id?
    egress_l3_binding_id?
    connection_state?
```

Не все поля известны на всех stages.

Например destination translation может применяться до egress route selection, а source translation — после неё.

## NATPolicy

Базовая configured policy:

```text
NATPolicy
    id
    default_transform
```

Rules в policy имеют deterministic order.

`default_transform` должен быть explicit.

Обычно он:

```text
IDENTITY
```

но backend не должен предполагать это без normalized fact.

## NATPolicyAttachment

Policy applicability задаётся отдельно:

```text
NATPolicyAttachment
    id
    policy_id
    local_stage_order
    scope
```

`scope` может использовать:

```text
traffic class
routing context
ingress interface / L3Binding
egress interface / L3Binding
```

Полный placement NAT stage относительно:

```text
route lookup
security stage
neighbor/L2 handoff
```

будет принадлежать `Packet Flow Trace`.

`local_stage_order` задаёт порядок только среди NAT stages, которые уже определены как применимые в одном processing hook.

## Vendor hooks не являются universal enum

Native термины:

```text
pre-routing
post-routing
before-policy
after-policy
central NAT
manual NAT
auto NAT
```

не должны становиться universal core order сами по себе.

Adapter должен сопоставить их с фактическим packet-processing plan конкретной платформы.

Native hook name сохраняется как evidence.

## NATRule

Концептуально:

```text
NATRule
    id
    policy_id
    order_key
    predicate
    transform
```

Rule identity не определяется display name или номером строки vendor config.

## Predicate

NAT rule использует ту же typed packet/context predicate semantics, что security rules.

Практически implementation может вынести общий:

```text
PacketPredicate
```

из нынешнего conceptual `SecurityPredicate`.

Минимально NAT matching может зависеть от:

```text
source/destination IP
protocol
source/destination port
routing context
ingress/egress binding
traffic class
connection/session state
```

Predicate evaluation остаётся:

```text
TRUE
FALSE
UNKNOWN
```

и использует ту же безопасную boolean algebra.

## Ordered first-match

Минимальная normalized NAT policy использует:

```text
first terminal matching rule wins
```

Adapter отвечает за преобразование native vendor NAT semantics в эквивалентный ordered semantic view.

Если native order не может быть надёжно нормализован:

```text
NATResult = UNKNOWN
```

а не guessed rule.

## UNKNOWN earlier rule

Как и в security policy:

```text
rule predicate = UNKNOWN
```

нельзя просто пропустить.

Логически существуют branches:

```text
rule matches
rule does not match
```

Если transformations этих possibilities приводят к различным downstream packet states/outcomes, result остаётся uncertain.

## NATTransform

Rule action:

```text
NATTransform
```

является декларативным описанием изменений packet fields.

Минимально:

```text
source_ip_transform?
destination_ip_transform?
source_port_transform?
destination_port_transform?
```

Отсутствующий field transform означает:

```text
PRESERVE
```

## FieldTransform

Conceptual field transform должен поддерживать как минимум следующие semantic classes:

```text
PRESERVE
REPLACE_EXACT
SELECT_FROM
MAP
```

Это не обязательно concrete enum БД; это минимальные способности transformation resolver.

## PRESERVE

Поле остаётся без изменения.

```text
src_ip 10.0.0.10
    ->
src_ip 10.0.0.10
```

## REPLACE_EXACT

Поле заменяется одним exact value.

```text
dst_ip 203.0.113.10
    ->
dst_ip 10.0.0.10
```

или:

```text
dst_port 8443
    ->
dst_port 443
```

## SELECT_FROM

Output выбирается из semantic set/range/pool.

Например:

```text
src_ip
    ->
{203.0.113.10 .. 203.0.113.20}
```

или:

```text
source_port
    ->
dynamic port range
```

Если exact allocation неизвестен, backend не выбирает случайное значение.

## MAP

Output вычисляется функцией, зависящей от input field.

Пример prefix-preserving/static network mapping:

```text
10.0.0.0/24
    <->
203.0.113.0/24
```

где host bits сохраняются.

Конкретный набор mapping operators не фиксируется до реального use case.

Главный invariant:

> mapping semantics должна быть declarative и воспроизводимой; нельзя хранить только свободный vendor config text.

## Identity transform

Явный:

```text
IDENTITY
```

означает:

```text
PacketState after == PacketState before
```

при этом matching rule считается terminal для текущей policy stage.

Это нужно для:

```text
NAT exemption
no-NAT rule
identity NAT
```

Нельзя моделировать exemption как просто отсутствие rule, потому что ранний identity rule может shadow последующие translations.

## SNAT

Простой source NAT:

```text
match:
    src 10.0.0.0/24
    egress WAN

transform:
    source_ip = 203.0.113.5
```

Результат:

```text
10.0.0.10 -> 198.51.100.20
```

становится:

```text
203.0.113.5 -> 198.51.100.20
```

Другие packet fields сохраняются.

## DNAT

Простой destination NAT:

```text
match:
    dst 203.0.113.10
    tcp/443

transform:
    destination_ip = 10.0.0.10
```

Результат:

```text
198.51.100.20 -> 203.0.113.10:443
```

становится:

```text
198.51.100.20 -> 10.0.0.10:443
```

## Port forwarding

Это не отдельный primitive:

```text
destination_ip   = 10.0.0.10
destination_port = 443
```

например из:

```text
203.0.113.10:8443
```

## PAT

PAT является transformation, где source или destination transport port также изменяется.

Например:

```text
source_ip   = 203.0.113.5
source_port = SELECT_FROM(40000..60000)
```

Exact allocated port может зависеть от runtime allocator/session state.

## Twice NAT

Одна transformation может изменить обе стороны:

```text
source_ip      -> ...
destination_ip -> ...
```

Не требуется отдельная topology entity.

## NAT pool

Reusable configured translation source может быть представлен:

```text
NATPool
    id
    address_set
    port_range?
```

Он является structured configuration fact.

Display name вроде:

```text
OUTSIDE_POOL
```

не определяет contents.

Pool может использоваться несколькими transforms.

## Pool membership не означает exact allocation

Configured:

```text
pool = {203.0.113.10 .. 203.0.113.20}
```

говорит о possible translation set.

Он не говорит, какой адрес выберет конкретный new flow.

Для structural analysis может быть достаточно:

```text
translated source ∈ pool
```

Exact packet trace требует selection semantics либо observed/session allocation.

## Symbolic / set-valued result

NAT transform не всегда даёт один exact packet.

Поэтому conceptual result может быть:

```text
one exact PacketState
```

или:

```text
set/constraint of possible PacketStates
```

Текущая boundary разделяет exact и symbolic representations:

```text
PacketState
    exact/current packet descriptor

NATPacketConstraint
    packet_base
    source/destination IP ranges?
    source/destination port ranges?
```

Absent constraint field сохраняет exact value из `packet_base`. Present constraint field задаёт множество допустимых outputs и не использует base field как будто это exact translated value.

Например dynamic SNAT:

```text
source_ip ∈ 203.0.113.0/28
source_port ∈ 40000..60000
```

Downstream resolver может:

- reasoning over constraint;
- exhaustive-branch все finite candidates, включая полный Cartesian product
  нескольких constrained fields, если set не превышает safety limit;
- либо вернуть `UNKNOWN`, если exact value необходим.

Current packet-processing executor materializes не более `64` exact
`PacketState`. При большей cardinality он не перечисляет первые 64 values, а
возвращает `UNKNOWN` с `PACKET_CONSTRAINT_EXPANSION_LIMIT`. Random,
representative, sampled и partial selection запрещены. Это bounded exhaustive
materialization, а не general symbolic algebra.

## NATTransformResult

Минимально:

```text
TRANSFORMED_EXACT
TRANSFORMED_CONSTRAINED
IDENTITY
UNKNOWN
CONFLICTING
```

### TRANSFORMED_EXACT

Output packet однозначно известен.

### TRANSFORMED_CONSTRAINED

Известен допустимый output set/range, но exact value не выбран.

### IDENTITY

Selected NAT semantics явно оставляет packet без изменения.

### UNKNOWN

Rule selection или transform result невозможно достоверно определить.

### CONFLICTING

Sources дают несовместимые translation conclusions.

## Почему constrained result полезен

Для вопроса:

```text
может ли traffic выйти в Internet?
```

может быть неважно, какой именно source port PAT будет выбран.

Но для последующего firewall rule:

```text
permit translated source only 203.0.113.10
```

разница между exact и pool constraint уже значима.

Поэтому uncertainty должна сохраняться структурированно, а не сводиться сразу к одному boolean.

## Stateful NAT

Dynamic NAT/PAT часто создаёт runtime mapping:

```text
original tuple
    <->
translated tuple
```

Для existing flow точная translation может определяться не policy rule заново, а существующим session/NAT binding.

## NATBindingObservation

Концептуально:

```text
NATBindingObservation
    original_flow_key
    translated_flow_key
    directionality
    source
    observed_at
```

Точная flow-key/session schema будет определена вместе с `Packet Flow Trace`.

Это operational observation, а не configured NAT rule.

## Existing session precedence

Если platform semantics говорит, что established flow использует existing NAT binding:

```text
session/binding lookup
```

предшествует new-flow NAT policy evaluation на соответствующем stage.

Core не должен повторно выбирать dynamic pool address для каждого packet существующей session.

## Reverse traffic

Reverse NAT **не вычисляется простым запуском forward NAT policy задом наперёд**.

Пример PAT:

```text
10.0.0.10:12345
    ->
203.0.113.5:50123
```

Ответ:

```text
198.51.100.20:443
    ->
203.0.113.5:50123
```

должен использовать existing translation binding:

```text
203.0.113.5:50123
    ->
10.0.0.10:12345
```

Policy itself может не содержать обратного literal rule.

## What-if simulation

Для hypothetical NEW flow NetMap может предсказать:

```text
possible translation
```

но не должен записывать permanent `NATBindingObservation`.

Если понадобится end-to-end what-if session simulation:

```text
ephemeral NAT/session state
```

живёт внутри trace execution и исчезает после query.

Диагностический trace не мутирует canonical operational state.

## Dynamic allocation availability

Configured pool не гарантирует, что новый allocation сейчас возможен.

В effective analysis могут потребоваться operational facts:

```text
pool available
pool exhausted
allocator state unknown
```

Точная model pool utilization откладывается.

Если exact new-flow forwarding зависит от availability, а state неизвестен:

```text
UNKNOWN
```

лучше, чем предположение, что адрес обязательно выдастся.

## Hairpin NAT

Hairpin/loopback NAT не требует отдельного фундаментального class.

Это обычная sequence:

```text
packet enters local processing
NAT transformation
routing/security stages
L2 delivery
```

в которой translated destination может находиться за тем же logical/physical side.

Корректность определяется processing pipeline, а не названием `hairpin`.

## Static one-to-one NAT

Static mapping:

```text
10.0.0.10 <-> 203.0.113.10
```

может быть represented declaratively через exact/mapped transforms.

Но bidirectionality не должна подразумеваться одним символом `<->`, если platform реально применяет разные rules/hooks в направлениях.

Adapter создаёт те semantic stages, которые реально существуют.

## Network/prefix translation

Prefix translation вроде:

```text
10.0.0.0/24 -> 203.0.113.0/24
```

может использовать `MAP` с сохранением host bits.

Это structured function, а не 256 materialized rules.

Exact mapping operator будет определён при реализации, если понадобится.

## Address-family translation

NAT64/NAT46 меняет не только IP value, но и address family/protocol framing.

Это richer packet transformation.

Базовая модель не запрещает такой future transform, но текущий минимальный `NATTransform` ориентирован прежде всего на same-family IPv4/IPv6 address/port translation.

NAT64 semantics откладывается до отдельного сценария.

## ICMP и embedded packet

Некоторые NAT implementations переписывают embedded headers в ICMP errors.

Эта semantics не входит в первое ядро.

Если понадобится generated/related packet tracing, packet model будет расширен.

## Fragments

Transport ports могут отсутствовать в non-initial fragments.

Если NAT rule/allocation зависит от port, а fragment state не позволяет его определить без session/reassembly context:

```text
predicate/transform = UNKNOWN
```

до появления fragment-aware semantics.

Backend не должен выдумывать port.

## Policy default

Complete `NATPolicy` имеет explicit `default_transform`.

Обычный пример:

```text
IDENTITY
```

Если все rules `FALSE`, применяется default.

Если policy/order incomplete:

```text
UNKNOWN
```

может быть необходим даже при seemingly no matching known rule.

## Partial ordered NAT policy

Как и firewall policy, NAT order чувствителен.

Known rule:

```text
100: src 10.0.0.0/24 -> SNAT pool A
```

в partial snapshot не доказывает, что он selected.

Неизвестный earlier:

```text
50: src 10.0.0.10 -> IDENTITY
```

мог бы shadow его.

Поэтому selected NAT rule требует достаточной order/completeness evidence.

## Authoritative query-scoped NAT result

Некоторые platforms могут предоставлять packet simulation/session lookup, который прямо сообщает:

```text
matched native NAT rule X
translated tuple Y
```

Такой query-scoped result может быть sufficient evidence даже без полного NAT policy import.

Его provenance должна быть сохранена.

## NATPolicySnapshot

Концептуально:

```text
NATPolicySnapshot
    id
    source
    observed_at
    completeness
```

Snapshot включает согласованный view:

```text
attachments
rule order
predicates
transforms
pools
defaults
```

Configured policy может versionироваться реже, operational bindings — отдельно.

## Configured NAT

Configured view отвечает:

> какую translation semantics задаёт известная конфигурация для new flow?

Он не должен зависеть от transient current session binding, если query специально не моделирует existing session.

## Effective NAT

Effective view может учитывать:

```text
existing NAT/session binding
current pool availability
active cluster/node
dynamic rule/object state
query-scoped platform result
```

Если authoritative runtime result существует, core не обязан симулировать allocator internals.

## Cluster/HA

В HA firewall current NAT/session state может принадлежать active member или синхронизироваться между members.

Core NAT model не делает HA node фундаментальным участником translation rule.

Source adapter должен дать usable effective binding/policy evidence.

Ownership/HA topology можно добавить отдельно.

## NAT и routing order

Destination translation может изменить route lookup:

```text
packet dst 203.0.113.10
    |
DNAT
    v
dst 10.0.0.10
    |
route lookup 10.0.0.10
```

А в другой platform/hook routing decision может происходить раньше.

NAT model **не фиксирует один universal order**.

Packet Flow Trace будет выполнять stages в platform-specific normalized `PacketProcessingPlan`.

## NAT и security order

Аналогично firewall rule может видеть:

```text
original destination
```

или:

```text
translated destination
```

в зависимости от pipeline.

Canonical security policy уже оценивает explicit current `PacketState`.

Поэтому правильная композиция:

```text
PacketState P0
    |
NAT -> P1
    |
Security evaluates P1
```

или:

```text
PacketState P0
    |
Security evaluates P0
    |
NAT -> P1
```

без изменения самих security/NAT primitives.

## NAT и egress scope

Некоторые source NAT rules выбираются по egress interface/zone.

Значит такой NAT stage должен выполняться после того, как pipeline уже знает appropriate egress.

`NATEvaluationContext.egress_l3_binding_id` тогда заполнен.

Если egress неизвестен, predicate может быть:

```text
UNKNOWN
```

или stage ещё не должен выполняться.

## NAT и recursive routing

Recursive next-hop lookup не является packet NAT processing.

Когда L3 resolver ищет route к gateway:

```text
lookup_address = gateway
```

он не создаёт новый packet и не запускает NAT над `lookup_address`.

NAT применяется к actual `PacketState` в processing pipeline, а не к internal resolver variables.

Это важный invariant.

NAT также не читает и не изменяет transient local mark. Local mark принадлежит `LocalProcessingState`, определённому в [[01-07-policy-routing|01.7 Policy Routing]].

## NAT и local delivery

DNAT может превратить external destination в адрес local service.

После translation следующая routing/local-delivery stage может получить:

```text
RouteDisposition = LOCAL
```

Это нормальный result композиции.

NAT itself не объявляет packet локально доставленным.

## NAT и L2

NAT не изменяет Ethernet/FDB topology напрямую.

После translation routing/neighbor resolution формирует appropriate destination MAC, а затем работает существующий L2 resolver.

NAT layer не должен изменять `L2Binding`/FDB.

## NATResult evidence

Каждая applied/identity NAT stage должна объяснять:

```text
policy
attachment/stage
matched rule или default
predicate evidence
PacketState before
PacketState after / constraints
source snapshot
native provenance
```

Пример:

```text
FW01 NAT stage
rule 42

before:
10.1.20.15:51234 -> 198.51.100.20:443

after:
203.0.113.5:55001 -> 198.51.100.20:443
```

или для dynamic unresolved allocation:

```text
after:
source_ip in POOL_A
source_port in 40000..60000
exact tuple unknown
```

## Coupled vendor rule provenance

Если native rule объединяет:

```text
security permit
SNAT
logging
```

canonical facts:

```text
SecurityRule
NATRule/Transform
side-effect evidence
```

могут иметь одну provenance group:

```text
native_rule_id = X
```

UI сможет снова показать их как одну vendor rule без смешивания core semantics.

## NAT result и end-to-end verdict

NAT сам по себе не имеет verdict:

```text
REACHABLE
BLOCKED
```

Он возвращает transformation outcome.

Например:

```text
TRANSFORMED_EXACT
```

ещё ничего не говорит о route/security после него.

End-to-end `Packet Flow Trace` агрегирует все layers.

## Инварианты

1. NAT является packet transformation, а не route и не security decision.
2. NAT работает над explicit current `PacketState`.
3. Packet lineage сохраняет before/after exact states или constrained result; предыдущий state не мутируется.
4. SNAT/DNAT/PAT/port-forward/twice-NAT являются производными labels над field transformations.
5. NAT rule predicate использует typed three-valued semantics.
6. UNKNOWN earlier rule нельзя молча пропускать.
7. Normalized NAT policy имеет deterministic ordered evaluation.
8. Native semantics, которые нельзя достоверно нормализовать, дают `UNKNOWN`.
9. NATTransform изменяет только явно указанные fields; остальные сохраняются.
10. Identity NAT является explicit terminal transform, а не отсутствием rule.
11. Dynamic pool не даёт права выбрать случайный exact translated value.
12. Transform может вернуть exact или constrained/set-valued packet result.
13. Exact packet trace не должен скрывать неопределённый dynamic allocation.
14. Existing dynamic flow может использовать `NATBindingObservation`.
15. Reverse dynamic NAT разрешается через binding/session semantics, а не запуском forward rule наоборот.
16. Diagnostic trace не создаёт persistent NAT/session binding.
17. Configured pool contents и runtime allocation availability являются разными facts.
18. Complete NAT policy имеет explicit default transform.
19. Partial ordered NAT policy обычно недостаточна для final selected-rule conclusion.
20. Query-scoped authoritative platform translation может быть самостоятельным evidence.
21. NAT configured/effective views различаются.
22. NAT model не фиксирует universal порядок относительно routing/security.
23. Routing recursion variables не являются PacketState и не проходят NAT.
24. NAT не изменяет L2 topology/FDB напрямую.
25. NAT result должен сохранять matched rule/default и before/after packet evidence.
26. Vendor combined security+NAT rule раскладывается на separate semantic effects с общей provenance.
27. NAT transformation outcome не является end-to-end reachability verdict.
