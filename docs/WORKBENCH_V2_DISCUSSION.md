## 1. Продуктовая идентичность

NetMap — Network Engineering Workbench: инженерная среда построения, изменения и анализа инфраструктурной модели, не клон NetBox/Nautobot и не обычная inventory/admin-панель. Canonical topology, физические конструкции, независимые members, установки компонентов, явная пассивная continuity, resolver/evidence — фундамент продукта. Существующий frontend остаётся функциональным инженерным инструментом; новый интерфейс проектируется как полноценная пользовательская среда, а не косметический редизайн.

Принципы будущего UX: плотная, но не перегруженная рабочая среда CAD/GIS/EDA; центральный холст или другой специализированный рабочий инструмент; дерево структуры/библиотеки, контекстный инспектор, нижняя область результатов, компактные toolbar и status bar, открытые рабочие вкладки; панели сворачиваются и изменяют размеры. Карта центральна при анализе инфраструктуры, но не является обязательным фоном конструктора, каталога или коммутации. Конструктор — полноценный CAD-подобный редактор с контекстным редактированием, FRONT/REAR/F+R, инструментами геометрии, точной разводкой и проверкой. Варианты визуального языка: Graphite Engineering (предпочтительная нейтральная тёмная база), Blueprint для схем, Industrial Utility, Technical Light. Цвет интерфейса отделять от семантики topology, совместимости, диагностики и trace; отсутствие измерений не изображать как сигнал. Ориентиры, не обязательные значения: текст 13–14 px, технические таблицы 12–13 px, строки 28–32 px, скругления 2–4 px, моноширинные технические значения, минимальная декоративность. Светлая тема возможна через design tokens. Сначала информационная архитектура и интерактивные прототипы, затем реализация.

## 2. Согласованная концепция владения

- NetMap instance: пользователи, управление доступом и Workspace.
- Workspace: независимая каноническая инфраструктурная модель и собственные каталоги. Новый Workspace по смыслу — чистая БД (без экземпляров оборудования/соединений); физическая PostgreSQL database vs логическая изоляция — отдельное техническое решение, не принято.
- Map: именованный организационный контейнер компоновок, НЕ владелец canonical topology и НЕ дополнительная граница принадлежности объектов. Вариант с собственной областью membership карты обсуждался и отвергнут в пользу контейнера.
- Layout (компоновка): сохранённое представление модели Workspace; определяет собственный membership и presentation state, координаты и геометрию визуальных линий, visibility, Location collapse, FRONT/REAR overrides, уровень детализации, отображаемый слой/вариант. Несколько компоновок могут показывать один PhysicalObject с разной геометрией; не дублировать канонические данные.
- Session: временный пользовательский контекст (выделение, открытые панели/вкладки, активная трасса); не превращать в общий persisted layout state. Какие личные предпочтения сохранять, как делиться layout и управлять конкурентными изменениями — ещё решить.
- Оборудование, Locations, интерфейсы, bindings, ConnectionPoint, Connection, ConnectionMember, Cable, определения и закреплённые ревизии принадлежат соответствующему Workspace. Между компоновками/картами одного Workspace canonical связи допустимы; между независимыми Workspace не создавать canonical cross-reference.

Три состояния: объект включён и видим; входит в компоновку, но скрыт (существующее поведение скрытия); не входит в компоновку — при отображении его связи с видимым окончанием явный указатель «Находится за пределами компоновки…» и разрешимый адрес объекта/окончания. Скрытие и исключение различаются, не меняют topology, не обрывают canonical trace. Оба состояния могут сосуществовать в одной компоновке (предложение координатора, детали уточнить). Сохранённая позиция скрытого сохраняется. Удаление из представления не удаляет объект из модели. Новая компоновка, дублирование, включение/исключение, скрытие/показ, перенос между картами того же Workspace — кандидаты операций; отдельные подтверждения для canonical delete. Физическое, логическое, пространственное и аналитическое представления — направления UX, не новые обязательные сущности.

Создание Workspace: «Новый Workspace» → пустая модель → создание первой карты/компоновки по выбору; выборочный импорт из другого Workspace (или экспортированного файла): физические типы и совместимость, шаблоны объектов/плат/трансиверов, Locations, справочники. Не переносить экземпляры оборудования/кабелей при импорте определений. Автоматически учитывать необходимые зависимости, явно показывать конфликт и итоговый состав, независимая копия без живых меж-Workspace зависимостей. Полный snapshot export/reset/import (сейчас Workspace JSON v17) отличать от выборочного импорта. Политика UUID при копировании между Workspace и conflict resolution требует отдельного контракта.

## 5. Политика UX v1 и FIELD_NOTES

После инженерного завершения L1 перевести frontend v1 в режим функциональной поддержки. Не делать масштабную визуальную переработку старого UI. Классифицировать все актуальные FIELD_NOTES (не закрывать и не удалять как выполненные):
- инженерная некорректность, потеря данных, неверная адресация/trace, occupancy, сохранение, canonical identity — исправлять до соответствующей приёмки;
- блокирующий инженерную проверку UX — минимальное исправление v1;
- чистый UX/visual debt (отступы, меню, общая компоновка, формы) — требования v2;
- новые возможности и семантика данных — отдельный контракт, не считать простой косметикой.

Примеры: FN-040/011/024/051 — v2; FN-052 — v2 при корректной текущей операции; FN-054 — не допускать инженерной недостоверности, визуальную переработку v2; FN-020 — v2 если не блокирует G1; FN-050 — инженерная диагностика; FN-022 — отдельная маркировка как контракт данных; FN-015 — массовая установка с серверной атомарностью. IA-01–IA-06, применимые обязательные UX-correctives и карта/collapse должны перейти в новый контракт G2 и быть проверены, а не исчезнуть. Список примеров не заменяет инвентаризацию актуального журнала.

## 6. Параллельные frontend

Рекомендуемая структура: app/ (backend), frontend/ (v1), frontend-next/ (v2), tests/, docs/. Два frontend контейнера с разными портами (например 3000/3001, фактические свободные порты проверить) и единый backend/API/каноническая БД при совместимых контрактах. v1 используется для рабочих сценариев, пока v2 неполон. Никакого прямого доступа frontend к БД. Экспериментальные backend-изменения, миграции и разрушительные тесты — отдельная тестовая БД/Compose project; основное окружение netmap и данные не трогать. При новых Workspace/ACL оба frontend подчиняются серверным границам; не оставлять legacy bypass, временная совместимость v1 только пока безопасна и нужна. При несовместимом контракте — адаптация v1 или отдельная среда, а не незащищённый API. Вывод v1 только после функциональной приёмки v2.

Параллельная реализация в разных git-ветках требует отдельных checkout/worktree и явного изменения текущего правила последовательных milestones. Docker сам по себе не изолирует файлы checkout. До согласования — не запускать параллельные coding-agent milestones. Прототипы на синтетических данных допустимы как концептуальная работа, без подключения к рабочей БД. Не переносить старую навигацию и state автоматически. Переиспользовать проверенные API/DTO, геометрию, pairing/валидацию, renderer/evidence там, где пригодно; оценить canvas engine на прототипе. React/TypeScript/Vite не заменять без обоснования. Не вводить speculative общую библиотеку только ради переиспользования.
