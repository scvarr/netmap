# 01.4 L3 — routing model

## Статус

Согласованная базовая концептуальная модель L3.

Алгоритмическая state machine определена в [[03-03-l3-trace|03.3 L3 Trace]].

Она фиксирует:

- IP address и prefix как сетевые value objects;
- локальный `RoutingContext`;
- привязку `NetworkInterface` к routing context;
- назначение IP-адресов;
- routing tables;
- routes и route dispositions;
- next-hop representation;
- recursive next-hop resolution;
- переход L3 -> neighbor resolution -> L2;
- configured/effective distinction;
- работу с неполными данными.

NAT, firewall/security policy, dynamic routing protocol state machine и exact ECMP hashing не входят в эту ветку. Выбор table и policy-based routing определены отдельным contract в [[01-07-policy-routing|01.7 Policy Routing]].

## Основной принцип

L3 не является глобальным графом:

```text
IP address -> gateway -> next device
```

Маршрут всегда рассматривается внутри routing context.

Концептуально:

```text
NetworkInterface
        |
      L3Binding
        |
   RoutingContext
        |
   RoutingTable
        |
       Route
        |
   RouteNextHop[]
```

После выбора next hop L3 resolver не прыгает сразу к другому router.

Он должен разрешить next hop через локальную link-layer среду:

```text
Route
    |
RouteNextHop
    |
next-hop IP / egress interface
    |
Neighbor resolution
    |
destination MAC
    |
L2 resolver
```

Это является основным мостом L3 -> L2.

## RoutingContext

Фундаментальная сущность:

```text
RoutingContext
    id
```

Она означает:

> локальное L3 namespace, внутри которого выполняются address interpretation и route lookup.

Типичные реализации:

```text
default routing instance
VRF
virtual router
Linux network namespace / routing domain
tenant routing context
```

Но backend не обязан иметь отдельные фундаментальные классы для каждого из них.

Человекочитаемое:

```text
alias.display = "VRF PROD"
class = vrf
```

может быть metadata/evidence.

Алгоритм использует стабильный `RoutingContext.id`.

## Почему контекст обязателен

Одинаковый IP может существовать одновременно:

```text
RoutingContext A:
    10.0.0.1

RoutingContext B:
    10.0.0.1
```

и это не конфликт.

Поэтому ни:

```text
IPAddress
```

ни:

```text
IPPrefix
```

сами по себе не определяют положение адреса в NetMap.

Контекст появляется через assignments, bindings, routes и trace state.

## Address family

Базовая модель должна поддерживать как минимум:

```text
IPv4
IPv6
```

Address family является свойством значения адреса/prefix, а не человекочитаемой metadata.

Алгоритм не должен пытаться route IPv4 address по IPv6 table и наоборот.

Расширение на иные address families возможно позднее, если появится реальный сценарий.

## IPAddress

`IPAddress` — нормализованный value object.

Например:

```text
192.0.2.10
2001:db8::10
```

Текстовый формат не определяет идентичность.

Для IPv6 эквивалентные textual representations должны нормализоваться к одному значению.

Конкретный physical DB type пока не фиксируется.

PostgreSQL `inet` является естественным кандидатом, но это уже решение реализации.

## IPPrefix

`IPPrefix` — отдельный value object:

```text
192.0.2.0/24
2001:db8:10::/64
0.0.0.0/0
::/0
```

Prefix должен быть канонизирован по network address.

Например:

```text
192.0.2.17/24
```

как prefix value нормализуется до:

```text
192.0.2.0/24
```

При этом интерфейсный address assignment всё ещё может хранить:

```text
address = 192.0.2.17
prefix_length = 24
```

То есть:

```text
interface address != network prefix
```

## L3Binding

Связь `NetworkInterface` с routing context задаётся явно:

```text
L3Binding
    id
    interface_id
    routing_context_id
```

Семантика:

> этот NetworkInterface участвует в данном L3 routing context.

Это L3-аналог explicit attachment, но он не заменяет `L2Binding`.

Один и тот же `NetworkInterface` может одновременно иметь:

```text
L2Binding
L3Binding
```

потому что это разные уровни semantics.

## Уникальность L3Binding

Базовая нормализация предполагает максимум один canonical direct binding для пары:

```text
(interface_id, routing_context_id)
```

Один interface может иметь несколько L3 bindings только если реальный сценарий действительно требует его участия в нескольких routing contexts.

Backend не должен выводить context из имени интерфейса.

Например:

```text
eth0.100
```

не означает автоматически конкретную VRF.

## InterfaceAddress

Назначение IP-адреса моделируется отдельно:

```text
InterfaceAddress
    id
    l3_binding_id
    address
    prefix_length
```

Семантика:

> адрес назначен интерфейсу в routing context этого `L3Binding`.

Один binding может иметь несколько addresses:

```text
primary/secondary IPv4
несколько IPv6 addresses
link-local + global
temporary addresses
virtual addresses
```

Термины `primary`, `secondary`, `temporary` могут быть дополнительными structured facts, если реально влияют на поведение.

## Scope адреса

Некоторые адреса требуют дополнительной области интерпретации.

Пример:

```text
IPv6 link-local fe80::/10
```

Такой адрес нельзя корректно использовать как глобально однозначный next hop без interface/scope information.

Модель next-hop должна поэтому позволять указать egress interface вместе с gateway address.

Backend не должен пытаться сделать link-local address глобально уникальным внутри всего routing context.

## Address ownership не означает reachability

Из:

```text
InterfaceAddress
    192.0.2.10/24
```

нельзя автоматически заключить:

```text
весь 192.0.2.0/24 сейчас reachable
```

Реальный forwarding зависит также от:

```text
interface state
routing table
point-to-point semantics
device configuration
neighbor/L2 state
```

Address assignment является фактом конфигурации/identity, а не готовым route result.

## Connected routes

Во многих системах interface address порождает connected route.

Но NetMap не обязан всегда синтезировать его из prefix length.

Предпочтительная semantic truth для trace:

```text
effective RoutingTable содержит connected/direct route
```

Adapter может вывести этот route из configuration, RIB/FIB или interface semantics.

Это важно для:

```text
point-to-point links
host routes
unnumbered interfaces
platform-specific connected behavior
```

## RoutingTable

Routing context содержит одну или несколько routing tables:

```text
RoutingTable
    id
    routing_context_id
    address_family
```

Простейший случай:

```text
RoutingContext default
├── IPv4 table
└── IPv6 table
```

Но модель допускает несколько tables одной family.

Это требуется для будущей поддержки:

```text
policy routing
Linux multiple tables
special lookup stages
vendor routing instances
```

Как именно выбирается table для конкретного packet — отдельная `ROUTING_POLICY` semantics, определённая в [[01-07-policy-routing|01.7 Policy Routing]].

После выбора `RoutingTable` становится explicit input для route-decision semantics. `ROUTE_DECISION` не определяет сам, какую из нескольких tables context использовать.

## Primary/default table

Для первого backend допустимо иметь понятие default/primary table для address family.

Но это должно быть явным relation/configuration, а не предположением:

```text
table with smallest ID
```

или:

```text
table named main
```

Имя таблицы не является алгоритмической истиной.

Explicit primary/default-table fact может участвовать в table selection, но не является hidden fallback внутри `ROUTE_DECISION`. Нельзя выбирать table по имени `main`, минимальному ID, display alias или insertion order.

## Route

`Route` является semantic forwarding entry:

```text
Route
    id
    routing_table_id
    destination_prefix
    disposition
```

Route identity не равна prefix.

Для одного prefix могут существовать:

```text
несколько observed candidates
несколько configured facts
несколько historical versions
ECMP next hops
conflicting sources
```

Поэтому нельзя использовать:

```text
UNIQUE(table_id, destination_prefix)
```

как универсальный domain invariant.

Конкретная effective table view должна разрешать, какие entries одновременно являются forwarding truth.

## RouteDisposition

Минимальная semantic disposition:

```text
FORWARD
LOCAL
DISCARD
```

### FORWARD

Packet должен быть передан далее через один или несколько next hops.

### LOCAL

Destination считается локально доставляемым внутри текущего routing context/device.

Это terminal L3 result или handoff в local stack/service semantics.

### DISCARD

Packet намеренно прекращает путь.

Это отличается от:

```text
NO_ROUTE
```

Потому что `DISCARD` является найденным routing decision.

Примеры vendor concepts:

```text
blackhole
reject
Null0
prohibit
unreachable route
```

могут нормализоваться более детально позже.

Базовый resolver не должен использовать строку `Null0` как магический interface.

## NO_ROUTE

`NO_ROUTE` не является `RouteDisposition`.

Это результат route lookup:

> ни один applicable route не найден.

Если routing table coverage известна как complete, это доказанный routing failure.

Если table data incomplete, отсутствие найденного route даёт `UNKNOWN`.

То же правило completeness, что и в L2/FDB, применяется и здесь.

## RouteNextHop

Для `FORWARD` route существует один или несколько:

```text
RouteNextHop
```

Минимальная семантика next hop должна позволять выразить:

```text
gateway IP
egress NetworkInterface
gateway IP + egress NetworkInterface
directly connected egress
```

Концептуально:

```text
RouteNextHop
    id
    route_id
    gateway_address?
    egress_l3_binding_id?
```

Оба поля не должны быть одновременно пустыми для `FORWARD`.

Конкретная SQL constraint будет определена позже.

## Почему next hop ссылается на L3Binding

Просто:

```text
egress_interface_id
```

может быть недостаточно, если interface участвует в нескольких routing contexts.

Поэтому scope-aware ссылка:

```text
egress_l3_binding_id
```

точнее отражает semantic egress.

Она однозначно даёт:

```text
NetworkInterface
RoutingContext
```

## Gateway-only next hop

Пример:

```text
0.0.0.0/0
    via 192.0.2.1
```

может не содержать заранее выбранный interface.

Тогда resolver должен рекурсивно определить, как gateway `192.0.2.1` reachable внутри текущего routing context.

## Interface-only next hop

Connected/direct route:

```text
192.0.2.0/24
    out Ethernet1
```

не обязан иметь gateway IP.

Для packet destination:

```text
192.0.2.50
```

link-layer neighbor target обычно становится самим destination IP:

```text
neighbor target = 192.0.2.50
```

а не отдельным gateway.

## Gateway + interface

Некоторые routes требуют одновременно:

```text
via fe80::1
out Ethernet1
```

Особенно это принципиально для IPv6 link-local next hop.

Interface ограничивает scope gateway resolution.

Модель обязана уметь сохранить обе части.

## ECMP / multiple next hops

Один effective `FORWARD` route может иметь несколько next hops:

```text
Route 10.20.0.0/16
├── via 192.0.2.1
└── via 192.0.2.2
```

Это candidate set.

Как и с LAG:

```text
candidate next hops != exact packet path
```

Structural reachability может исследовать все допустимые next hops.

Exact packet trace может требовать:

```text
ECMP hash policy
packet fields
runtime forwarding state
```

Если exact choice неизвестен, engine не выбирает next hop случайно.

## Next-hop weight / preference

Weight, group member state и другие attributes должны становиться структурированными только если используются forwarding selection.

Не следует заранее складывать все vendor route attributes в core `RouteNextHop`.

Raw attributes могут сохраняться как provenance.

## Longest Prefix Match

При обычном destination-based lookup применима semantic operation:

```text
destination IP
    ->
all applicable prefixes
    ->
longest prefix match
```

Пример:

```text
10.0.0.0/8
10.20.0.0/16
10.20.30.0/24
```

для:

```text
10.20.30.55
```

наиболее специфичен:

```text
10.20.30.0/24
```

Но LPM — только часть полного route selection pipeline.

## Не симулировать control plane без необходимости

Несколько protocol candidates могут существовать:

```text
BGP
OSPF
static
connected
```

Чтобы выбрать installed route, реальное устройство применяет:

```text
administrative preference
metric
protocol rules
policy
recursive resolution
```

NetMap не должен автоматически превращаться в симулятор всех routing protocols.

Предпочтительный adapter path:

```text
vendor config / RIB / FIB
        |
normalize
        v
effective semantic RoutingTable
```

Исходные protocol candidates и selection evidence можно сохранять отдельно.

## Protocol source

Такие значения, как:

```text
connected
static
OSPF
BGP
IS-IS
kernel
```

полезны для объяснимости и диагностики.

Но они не являются разными фундаментальными subclasses `Route`.

Если source влияет на route selection в configured analysis, он становится structured selection fact/evidence соответствующего resolver, а не hardcoded topology class.

## Configured и effective routing

Как и L2, L3 должен различать:

```text
configured routing
effective routing
```

### Configured

Отвечает примерно:

> какой forwarding intent можно вывести из известной конфигурации?

### Effective

Отвечает:

> какой route/next-hop сейчас считается фактически установленным/используемым?

Effective view может зависеть от:

```text
interface operational state
route installation state
next-hop reachability
dynamic protocol state
recursive resolution
```

Adapter может получить effective view непосредственно из FIB/RIB и не заставлять core пересчитывать control plane.

## RoutingTableSnapshot

Operational/effective routing table быстро меняется.

Для reproducible trace естественна snapshot semantics:

```text
RoutingTableSnapshot
    id
    routing_table_id
    source
    observed_at
    completeness
```

Routes могут относиться к snapshot или к configured plane.

Точная physical schema пока не фиксируется.

Инвариант уже знакомый:

> отсутствие route в неполном snapshot не доказывает NO_ROUTE.

## Completeness

Минимальная completeness для snapshot может использовать общую cross-cutting semantics:

```text
COMPLETE
PARTIAL
UNKNOWN
```

При:

```text
COMPLETE + fresh + no matching route
```

допустим доказанный:

```text
NO_ROUTE
```

При partial/unknown/stale data:

```text
UNKNOWN
```

если отсутствие route критично для вывода.

## Route lookup result

Минимально route resolver может возвращать:

```text
ROUTE_FOUND
NO_ROUTE_CONFIRMED
UNKNOWN
CONFLICTING
```

### ROUTE_FOUND

Есть достаточно достоверный selected/effective route result.

### NO_ROUTE_CONFIRMED

Полная релевантная table view подтверждает отсутствие route.

### UNKNOWN

Data отсутствует, incomplete, stale или не позволяет определить installed route.

### CONFLICTING

Несколько фактов дают несовместимые selected-route conclusions.

## Recursive next-hop resolution

Gateway next hop сам может требовать route lookup.

Пример:

```text
Route A:
    203.0.113.0/24 via 192.0.2.1

Route B:
    192.0.2.0/24 out Ethernet1
```

Resolution:

```text
203.0.113.7
    |
Route A
    |
gateway 192.0.2.1
    |
Route B
    |
Ethernet1
```

После этого gateway считается directly reachable через Ethernet1.

## Recursive state

Resolver должен сохранять:

```text
routing_context
routing_table_id
gateway address
visited resolution states
```

чтобы:

- объяснять цепочку;
- обнаруживать recursion loop;
- не смешивать одинаковые addresses из разных contexts.

## Recursive loop

Пример ошибочной routing configuration:

```text
A via B
B via A
```

не должен приводить к бесконечному resolver.

Termination:

```text
LOOP_DETECTED
```

и общий exact trace:

```text
UNKNOWN
```

или известный routing failure согласно semantics query.

Конкретный verdict aggregation будет определён в L3 trace branch.

## Next-hop resolution result

После recursive route resolution `FORWARD` branch должен прийти к одному из состояний:

```text
DIRECT_EGRESS
LOCAL
DISCARD
UNKNOWN
```

### DIRECT_EGRESS

Известны:

```text
egress L3Binding
neighbor target IP
```

### LOCAL

Packet доставляется локально.

### DISCARD

Routing decision намеренно прекращает forwarding.

### UNKNOWN

Не удалось достоверно разрешить route/next-hop.

## Neighbor resolution

Для Ethernet-like L2 handoff direct egress ещё не всегда даёт concrete destination MAC.

Нужен semantic neighbor fact:

```text
NeighborEntry
    l3_binding_id
    ip_address
    mac_address
```

Это нормализует:

```text
ARP
IPv6 NDP
static neighbor
controller/overlay neighbor information
```

Но `NeighborEntry` не является обязательным условием **структурной L3 reachability**.

Следует различать:

```text
L3 Reachability
    next-hop identity -> target NetworkInterface/L3Binding
    -> L2 Reachability
```

и:

```text
IP Packet Trace
    concrete NeighborEntry / concrete destination MAC
    -> L2 Frame Trace
```

Если neighbor cache пуст, устройство может выполнить ARP/NDP при реальной отправке. Поэтому даже полный cache snapshot без entry сам по себе не доказывает L3-недостижимость.

Core L3 resolver не обязан моделировать ARP/NDP protocol state machine целиком.

## Почему NeighborEntry привязан к L3Binding

Neighbor mapping:

```text
192.0.2.1 -> aa:bb:cc:dd:ee:ff
```

не является глобальным.

Одинаковый IP может существовать:

```text
в другой VRF
на другом interface
на другом point-to-point/link context
```

Поэтому neighbor fact scope-aware:

```text
L3Binding + IP -> MAC
```

## Neighbor snapshot

Как и FDB, operational neighbor cache требует времени и completeness.

Концептуально:

```text
NeighborSnapshot
    l3_binding_id
    source
    observed_at
    completeness
```

и:

```text
NeighborEntry
    snapshot_id
    ip_address
    mac_address
    state?
```

Точная модель neighbor states будет уточнена при L3 trace.

## ARP/NDP states

Vendor/kernel states вроде:

```text
REACHABLE
STALE
DELAY
PROBE
INCOMPLETE
FAILED
permanent
```

не должны автоматически становиться core topology enum.

Adapter должен нормализовать их к вопросу:

> есть ли сейчас usable link-layer resolution для данного next-hop?

Protocol-specific state сохраняется как evidence.

## Neighbor absence

Как и FDB:

```text
нет NeighborEntry в NetMap
```

не означает:

```text
neighbor не существует
```

без snapshot completeness/freshness.

Это может означать:

```text
cache не собран
cache incomplete
entry aged out
host ещё не ARP-ился
```

Exact effective trace должен сохранять `UNKNOWN`.

## Direct destination

Для directly connected route:

```text
destination = 192.0.2.50
out Ethernet1
```

neighbor target обычно:

```text
192.0.2.50
```

Resolution:

```text
Route
    |
DIRECT_EGRESS(Ethernet1, 192.0.2.50)
    |
NeighborEntry
    |
dst MAC
```

## Gateway destination

Для gateway route:

```text
destination = 203.0.113.10
via 192.0.2.1
out Ethernet1
```

neighbor target:

```text
192.0.2.1
```

а не конечный destination:

```text
203.0.113.10
```

Это принципиальная часть L3 -> L2 handoff.

## L3 -> L2 handoff

После neighbor resolution:

```text
egress L3Binding
    |
NetworkInterface
    |
neighbor destination MAC
    |
L2 frame descriptor
    |
L2 resolver
```

Например:

```text
IP packet dst 203.0.113.10
    |
route via 192.0.2.1
    |
neighbor 192.0.2.1 = aa:bb:cc:dd:ee:ff
    |
Ethernet frame dst aa:bb:cc:dd:ee:ff
    |
L2 trace
```

L3 resolver не должен самостоятельно повторять FDB/STP/LAG/L1 logic.

Он вызывает уже определённый L2 semantic resolver.

## Source MAC

Чтобы сформировать Ethernet frame, может потребоваться source MAC соответствующего egress interface.

Он разрешается через `MacAssignment`/local L2 semantics.

Если exact source MAC необходим дальнейшей логике, но неоднозначен, trace должен сохранить это как uncertainty.

Для простой L3 reachability source MAC может не быть значимым.

## L2 context выбора

`L3Binding` и `L2Binding` независимы, но могут сходиться на одном `NetworkInterface`.

Например SVI:

```text
L2ForwardingContext
        |
     L2Binding
        |
NetworkInterface Vlan100
        |
     L3Binding
        |
RoutingContext
```

Это естественный handoff между L2 и L3.

Рouted physical/subinterface также может участвовать в L3 через свой `NetworkInterface`; соответствующая L2 boundary semantics определяется существующей L2/realization моделью.

L3 не должен выводить VLAN/tagging из IP prefix.

## Local delivery

Если selected route disposition:

```text
LOCAL
```

L3 trace достигает local endpoint/stack.

Это может означать:

```text
адрес самого router
SVI address
loopback
service endpoint
control plane
```

Дальнейшая обработка выше L3 относится к packet-flow/security/service semantics.

## Discard

Если:

```text
RouteDisposition = DISCARD
```

trace должен объяснить:

```text
routing decision found
packet intentionally discarded
```

Это диагностически отличается от:

```text
NO_ROUTE
```

и от:

```text
UNKNOWN
```

## Default route

Default route не требует специальной entity:

```text
0.0.0.0/0
::/0
```

являются обычными `IPPrefix`.

LPM naturally выбирает их, если более специфичный route отсутствует.

## Host route

Аналогично:

```text
192.0.2.10/32
2001:db8::10/128
```

являются обычными prefixes.

Специальный класс `HostRoute` не требуется.

## Point-to-point

Point-to-point link не должен требовать fake subnet semantics.

Если effective route говорит:

```text
destination/prefix
    out interface X
```

resolver может следовать этому fact независимо от того, выглядит ли interface address как привычная Ethernet subnet.

Это одна из причин не выводить routes исключительно из `InterfaceAddress.prefix_length`.

## Unnumbered interface

Модель также не требует IP address на каждом egress interface.

Если routing/next-hop facts однозначно указывают egress, `L3Binding` может существовать без `InterfaceAddress`.

Neighbor/link-layer resolution для конкретной технологии может потребовать отдельной semantics.

## Route eligibility и interface state

Даже найденный effective route не гарантирует успешный forwarding.

После выбора egress применяются operational gates:

```text
L3Binding / NetworkInterface usable?
next hop resolvable?
L2 path usable?
```

Состояние `NetworkInterface` уже определено в [[01-03-02-l2-operational-state|01.3.2 L2 Operational State]] как cross-layer forwarding eligibility.

При необходимости L3-specific eligibility может быть добавлена отдельным subject/fact, но не следует дублировать interface-down state.

## Routing protocols как provenance

Пример объяснения trace:

```text
10.20.30.40
    -- route 10.20.0.0/16 -->
next hop 192.0.2.1

evidence:
    installed route
    source protocol = OSPF
    metric = 20
    collected from router R1 at T
```

Core engine использует semantic selected route.

Пользователь всё равно видит знакомое объяснение, откуда route взялся.

## Route history

Routing table может меняться без изменения физической topology.

Например:

```text
T1: prefix X via R2
T2: prefix X via R3
```

Это temporal routing state.

Исторические snapshots нужны для воспроизводимой диагностики, но не должны изменять identity физических/network objects.

## Policy routing и граница route decision

Destination-only LPM не покрывает source-based routing, local fwmark, ingress-interface policy, DSCP/class-based policy и multiple tables.

Согласованный processing contract определён в [[01-07-policy-routing|01.7 Policy Routing]]:

```text
PACKET_MARK
    ->
ROUTING_POLICY
    -> selected RoutingTable
    ->
ROUTE_DECISION
```

Local mark является transient `LocalProcessingState`, а не `PacketState` field. `ROUTING_POLICY` выбирает table. `ROUTE_DECISION` выполняет LPM и next-hop resolution только внутри уже выбранной table и никогда скрыто не выбирает другую.

При recursive gateway lookup сохраняется тот же `routing_table_id`; policy selection заново не запускается. Базовая domain model допускает несколько `RoutingTable` на один `RoutingContext`, а concrete policy entities/storage остаются отдельным implementation slice.

## ECMP и packet descriptor

Exact ECMP selection может зависеть от:

```text
src/dst IP
protocol
src/dst port
flow label
vendor hash
hardware state
```

Structural L3 reachability может исследовать все candidate next hops.

Packet trace должен либо:

- выбрать next hop по известной policy;
- вернуть набор possible branches;
- либо сохранить exact path как `UNKNOWN`.

Случайный выбор запрещён.

## NAT не входит в Route

Нормализованная packet transformation model определена в [[01-06-nat|01.6 NAT — packet transformation]].

NAT не является свойством `Route`.

Route отвечает:

> куда forwarding plane пытается отправить текущий packet в текущем routing state?

NAT изменяет packet identity/state и относится к packet-flow/security processing.

Он будет моделироваться отдельно.

Это предотвращает смешивание:

```text
routing
address translation
firewall policy
```

в одну сущность.

## Firewall не входит в Route

Нормализованная security model определена в [[01-05-security-policy|01.5 Security Policy]].

Аналогично:

```text
Route exists
```

не означает:

```text
packet allowed
```

L3 resolver может доказать routing path, после чего security resolver остановит packet.

Будущий packet-flow trace композиционно объединит оба результата.

## Canonical / observed / derived

### Устойчивые/конфигурационные facts

Могут включать:

```text
RoutingContext
L3Binding
InterfaceAddress
RoutingTable
configured Route
configured RouteNextHop
```

### Operational observations

Могут включать:

```text
installed/effective routes
RoutingTableSnapshot

```

### Derived results

```text

```

Derived result не становится независимым source of truth.

## Минимальное концептуальное ядро

```text
RoutingContext
    |
    +-- RoutingTable
    |       |
    |      Route
    |       |
    |      RouteNextHop[]
    |
    +-- L3Binding -- NetworkInterface
            |
      InterfaceAddress[]
```

Operational bridge to L2:

```text
RouteNextHop
    |
recursive/direct resolution
    |
egress L3Binding + neighbor target IP
    |
NeighborEntry
    |
destination MAC
    |
L2 resolver
```

## Инварианты

1. L3 address/route interpretation всегда выполняется внутри `RoutingContext`.
2. `VRF` не является обязательным фундаментальным class name; core использует `RoutingContext`.
3. Одинаковый IP может существовать в разных routing contexts.
4. `IPAddress` и `IPPrefix` являются normalized value objects.
5. `InterfaceAddress` принадлежит `L3Binding`, а не глобально `NetworkInterface` без context.
6. Interface address assignment не является доказательством effective connected reachability.
7. `RoutingTable` принадлежит routing context и address family.
8. Routing context может иметь несколько tables.
9. Route identity не равна destination prefix.
10. `RouteDisposition` минимум различает `FORWARD`, `LOCAL`, `DISCARD`.
11. `NO_ROUTE` является lookup result, а не route disposition.
12. `FORWARD` route имеет хотя бы один semantic next hop.
13. Next hop может задавать gateway, egress L3 binding или оба.
14. Gateway-only next hop допускает recursive resolution.
15. Interface-only next hop допускает direct neighbor resolution конечного destination.
16. IPv6 link-local next hop может требовать explicit egress interface scope.
17. ECMP candidate set не означает exact packet path.
18. LPM применяется внутри уже выбранной routing table и не выполняет routing-policy selection.
19. Core не обязан симулировать OSPF/BGP control plane, если adapter предоставляет selected/effective routing result.
20. Dynamic protocol names являются provenance/selection evidence, а не subclasses topology.
21. Effective routing observations имеют temporal semantics.
22. Отсутствие route в incomplete/stale data не доказывает `NO_ROUTE`.
23. Recursive resolution обязана обнаруживать loops.
24. Neighbor mapping scope-aware и относится к `L3Binding`.
25. Отсутствие neighbor entry без completeness не доказывает отсутствия neighbor.
26. L3 resolver после neighbor resolution передаёт frame существующему L2 resolver.
27. L3 resolver не дублирует FDB/STP/LAG/L1 algorithms.
28. `LOCAL`, `DISCARD`, `NO_ROUTE` и `UNKNOWN` являются диагностически различными результатами.
29. Default/host routes являются обычными IP prefixes, а не специальными entity classes.
30. L3 model не требует numbered interface для каждого egress.
31. NAT не является свойством Route.
32. Firewall allow/deny не является свойством Route.
33. Derived L3 path не становится независимым source of truth.
34. `ROUTE_DECISION` не выбирает `RoutingTable`; selected table приходит из explicit table-selection semantics.
35. Recursive next-hop lookup использует ту же selected table и не перезапускает `ROUTING_POLICY`.

## Открытые вопросы

Следующие ветки намеренно откладываются:

- concrete storage/API для согласованной policy-routing semantics;
- effective route snapshot schema;
- route precedence/conflict resolver;
- exact ECMP selection;
- neighbor usability normalization и freshness;
- proxy ARP / proxy NDP;
- IPv6 RA/on-link semantics;
- unnumbered next-hop resolution;
- MPLS и другие L3/L2.5 labels;
- tunnel/overlay recursion;
- historical `at_time` routing trace;
- NAT;

Следующий логичный шаг — формализовать `L3 Trace` поверх этой модели: route lookup, recursion, neighbor resolution, L2 handoff, terminal outcomes и общий verdict.
