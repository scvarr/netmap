# 01.1 L1 — физическая модель

## Статус

Рабочая концептуальная модель. Фиксируются только уже согласованные инварианты; детали реализации БД и API пока не определяются.

## Минимальное ядро

```text
Location
PhysicalObject
ConnectionPoint
Connection
Metadata
```

L1-граф строится вокруг точек соединения и связей между ними. `PhysicalObject` группирует точки, `Location` задаёт пространственную иерархию, metadata даёт человеку названия и классификацию.

## Location

`Location` — узел произвольного дерева местоположений.

Концептуально:

```text
Location
    id
    parent_id
    path
```

Для хранения дерева планируется PostgreSQL `ltree`.

Backend не содержит фиксированных уровней `building`, `floor`, `room`, `rack`, `unit`. Семантика узлов задаётся aliases/metadata.

Пример одного дерева:

```text
Площадка
└── Здание
    └── Этаж
        └── Помещение
            └── Стойка
                └── Unit
```

Другой экземпляр может иметь совершенно другую структуру:

```text
Площадка
└── Уличная территория
    └── Колодец
        └── Муфта
```

Структура дерева и человекочитаемые названия независимы.

## PhysicalObject

`PhysicalObject` — универсальная сущность для любого физически существующего объекта, который требуется учитывать в модели.

Концептуально:

```text
PhysicalObject
    id
    parent_object_id?
    location_id?
```

Отдельных фундаментальных типов `Device`, `PatchPanel`, `Outlet`, `Cable`, `SFP`, `Cassette` и т. п. нет. При необходимости такие определения являются metadata.

Примеры metadata:

```text
alias.display = "SW-CORE-01"
class = "switch"
vendor = "..."
model = "..."
```

или:

```text
alias.display = "FO-DC1-DC2-017"
class = "cable"
medium = "fiber"
```

Ни одна из этих меток не влияет на идентичность объекта.

## Два независимых дерева

`Location` и вложенность `PhysicalObject` описывают разные отношения и не должны смешиваться.

### Location отвечает на вопрос

> Где находится объект?

Например:

```text
Площадка
└── Серверная
    └── Стойка R12
        └── Unit 17
```

Коммутатор может иметь `location_id`, указывающий на `Unit 17`.

### parent_object отвечает на вопрос

> Частью какого физического объекта является данный объект?

Например:

```text
шасси
└── модуль
    └── трансивер
```

или:

```text
корпус кросса
└── кассета
```

Установка устройства в стойку не делает стойку его `parent_object`. Подключение кабеля к устройству также не создаёт отношение parent/child.

`parent_object_id` означает только физическую композицию/вложенность.

## Инварианты вложенности PhysicalObject

- У объекта не более одного непосредственного `parent_object`.
- Циклы запрещены.
- Корневой объект может не иметь `parent_object`.
- Дочерний объект остаётся самостоятельной сущностью со своим стабильным ID, metadata и ConnectionPoint.
- Вложенность не означает сетевую связанность.
- Вложенность не означает местоположение.

Таким образом `PhysicalObject` образует лес независимых деревьев композиции.

## Наследование местоположения

`location_id` может быть задан явно не на каждом дочернем объекте.

Эффективное местоположение объекта определяется так:

1. используется собственный `location_id`, если он задан;
2. иначе используется эффективное местоположение ближайшего предка `PhysicalObject`;
3. если оно не найдено, местоположение считается неизвестным или неприменимым.

Это позволяет хранить:

```text
SW-01                      location = Rack-12 / Unit-17
└── line-card              location = inherited
    └── SFP                location = inherited
```

без копирования одного `location_id` во все дочерние записи.

Перемещение родительского объекта автоматически меняет эффективное местоположение его дочерних объектов, если у них нет явного override.

## Позиции внутри составного объекта

Номер слота, кассеты, отсека и аналогичные человекочитаемые обозначения не зашиваются в модель.

Простой случай задаётся metadata дочернего объекта:

```text
parent_object = chassis-01
position = "slot 3"
```

Если в будущем потребуется стабильная идентичность самого посадочного места независимо от установленного модуля, его можно представить отдельным `PhysicalObject`:

```text
chassis
└── slot-3
    └── module
```

Новая фундаментальная сущность `Slot` для этого не требуется.

## ConnectionPoint

`ConnectionPoint` — атом физической коммутации и принадлежит одному `PhysicalObject`.

Концептуально:

```text
ConnectionPoint
    id
    owner_id
    location_id?
    cardinality
```

Человекочитаемые обозначения точки являются metadata:

```text
alias.display = "Gi1/0/17"
```

или:

```text
alias.display = "17 front"
```

`location_id` точки является необязательным override. Если он не задан, точка наследует эффективное местоположение своего `PhysicalObject`.

Это позволяет объекту иметь точки в разных местах.

## Кабели и объекты, занимающие несколько мест

Кабель учитывается как обычный `PhysicalObject`, но модель не требует, чтобы любой `PhysicalObject` имел ровно одно местоположение.

Например, кабель между двумя зданиями может иметь две конечные `ConnectionPoint`, каждая со своим location override:

```text
Cable
├── endpoint A    location = Building-A / Room-1
└── endpoint B    location = Building-B / Room-2
```

Сам кабель при этом может не иметь единственного `location_id`.

Будущая трасса кабеля через лотки, шахты, колодцы и другие промежуточные места должна моделироваться отдельно. Она не должна превращать дерево Location в описание линейного маршрута кабеля.

## Кардинальность и Connection

Модель должна поддерживать многоканальные физические точки и линии, включая индивидуальную трассировку волокон, пар и других каналов. Технологическая семантика при этом не зашивается в ядро.

`ConnectionPoint.cardinality` задаёт число адресуемых members точки на выбранной глубине модели. Это именно разрешение модели, а не физическая спецификация разъёма. Например, RJ45 можно учитывать как одну неделимую точку с `cardinality = 1`, если отдельные пары не требуется трассировать.

`Connection.cardinality` задаёт число пар members, реально соединённых данной связью. Связь может использовать все или только часть members своих ConnectionPoint.

Фактическое сопоставление каналов хранится явно через `ConnectionMember`. Подробная модель и инварианты вынесены в отдельную ветку:

- [[01-01-01-connections|01.1.1 Connection и cardinality]]

Тип соединения не является фундаментальным классом. Такие характеристики, как `patch cord`, `permanent cable`, `splice`, `internal wiring`, `fiber`, `copper` и аналогичные, задаются metadata.

## Protocol-neutral L1 foundation

**FIXED compatibility boundary**

`PhysicalObject`, `ConnectionPoint`, `Connection` / `ConnectionMember`,
`NetworkInterface`, `InterfacePhysicalBinding` и
`NetworkInterfaceRealization` образуют protocol-neutral foundation. Они могут
представлять Ethernet, Fibre Channel и другие physical/network technologies;
существующие Ethernet-oriented examples не сужают этот contract.

Например, physical Fibre Channel path:

```text
Host HBA
    -> SFP
    -> fiber
    -> patch panel
    -> fiber
    -> SAN switch
    -> fiber
    -> storage controller
```

использует те же `PhysicalObject`, `ConnectionPoint` и explicit
`Connection` / `ConnectionMember`, что и любой другой L1 path. Для FC не нужен
отдельный cable, connection или L1 traversal primitive. Технологические facts
могут быть представлены отдельными future structured domains поверх этой
foundation, но не выводятся из `class`, aliases или типа кабеля.

## Metadata и aliases

Человекочитаемые названия и классификации не входят в идентичность сущностей.

Концептуально используется общий механизм:

```text
Metadata
    entity_id
    key
    value
```

Он должен быть применим как минимум к:

- Location;
- PhysicalObject;
- ConnectionPoint;
- Connection.

Примеры:

```text
alias.display
alias.short
alias.legacy
class
role
vendor
model
inventory_id
```

Переименование объекта не изменяет его ID и не изменяет топологию.

Текущий backend materialize bounded subset общего механизма metadata:
`alias.display` для `PhysicalObject`, `NetworkInterface` и `ConnectionPoint`, а
также произвольную непустую строку `class` только для `PhysicalObject`. Storage
сохраняет typed target relation ровно к одному entity; `class` не выводится из
aliases, количества точек/интерфейсов или connectivity. Остальные metadata keys
и entity kinds остаются будущими расширениями, а не неявной строковой semantics.

## Текущий L1-граф

На концептуальном уровне:

```text
ConnectionPoint  <── belongs to ──  PhysicalObject
      │                                │
      │                                ├── parent_object ──> PhysicalObject
      │                                │
      │                                └── located_at ─────> Location
      │
      ├──── Connection ──── ConnectionPoint
      │
      └── optional located_at ────────> Location
```

`Location` и `PhysicalObject.parent_object` являются независимыми иерархиями.

## Не решаем на этом этапе

- схему таблиц и индексов;
- конкретный backend-язык;
- API;
- UI и способ визуализации;
- конкретные типы кабелей и разъёмов;
- конкретные типы оборудования;
- кабельные маршруты через промежуточные Location;
- L2/L3/Security.

## Граница с сетевыми уровнями

Связь L1 с логическими сетевыми интерфейсами вынесена в отдельную ветку:

- [[01-02-network-interface|01.2 NetworkInterface — граница L1 и сетевых уровней]]

`ConnectionPoint` остаётся атомом физического подключения и не превращается в сетевой интерфейс. Мост между L1 и сетевыми уровнями задаётся явным `InterfacePhysicalBinding`.
