# 01.1.1 Connection и cardinality

## Статус

Согласованная концептуальная модель многоканальной физической связи. Реализация таблиц и индексов пока не фиксируется.

## Цель

Одна и та же модель должна описывать:

- одиночное физическое соединение;
- многоволоконный кабель;
- многопарный или многожильный носитель;
- splice/сварку;
- внутреннюю разводку пассивного объекта;
- MPO и другие многоканальные разъёмы;
- breakout с разным количеством ConnectionPoint на сторонах.

Понятия `fiber`, `pair`, `wire`, `MPO`, `splice` и конкретные типы кабелей не входят в ядро и при необходимости задаются metadata.

## Уровень детализации

Кардинальность описывает число **адресуемых и независимо трассируемых members в модели**, а не обязательное число физических проводников внутри изделия.

Поэтому один и тот же класс физического разъёма может моделироваться на разной глубине. Например, RJ45 допустимо учитывать как:

```text
cardinality = 1
```

если Ethernet-линия рассматривается как неделимая физическая связь. Если когда-либо потребуется трассировка отдельных пар, модель может использовать более высокую кардинальность.

Backend не выводит кардинальность из `medium`, `connector`, `class` или других metadata.

## ConnectionPoint.cardinality

`ConnectionPoint.cardinality` — количество адресуемых members точки.

Концептуально точка `P` с `cardinality = N` содержит позиции:

```text
P:1
P:2
...
P:N
```

Member точки является координатой внутри ConnectionPoint. На текущем уровне он не обязан быть отдельным `PhysicalObject`.

Примеры:

```text
обычный атомарный порт       cardinality = 1
многоволоконная точка        cardinality = 48
многоканальный разъём        cardinality = 12
```

Неиспользуемые members допустимы.

## Connection

`Connection` — недиректная бинарная физическая связь ровно между двумя `ConnectionPoint`.

Концептуально:

```text
Connection
    id
    point_a_id
    point_b_id
    cardinality
```

Стороны `A` и `B` нужны только для стабильного хранения mapping и не задают направление передачи. На L1 `Connection` недиректна.

`Connection` всегда связывает две точки. Разветвления не представляются гиперребром: splitter, breakout и другие разветвляющие конструкции моделируются через `PhysicalObject` с несколькими ConnectionPoint и несколькими Connection.

## Connection.cardinality

`Connection.cardinality` — количество пар members, реально соединённых данной связью.

Пример:

```text
point A cardinality = 48
point B cardinality = 48
connection cardinality = 12
```

означает, что данная связь соединяет только 12 пар каналов этих точек. Остальные members могут быть свободны или участвовать в других Connection.

Кардинальность Connection является свойством mapping. Каноническая истина — явный набор `ConnectionMember`. Если `cardinality` физически хранится в записи Connection, оно должно быть равно количеству его ConnectionMember. Оно также может быть вычисляемым полем.

## ConnectionMember

Каждая реально соединённая пара members представляется явно.

Концептуально:

```text
ConnectionMember
    id
    connection_id
    index
    point_a_member
    point_b_member
```

Например:

```text
Connection C1
A = CP-100, cardinality 48
B = CP-200, cardinality 48

member 1:  A:17 <-> B:4
member 2:  A:18 <-> B:7
member 3:  A:19 <-> B:8
```

Это позволяет хранить произвольную перестановку каналов без специальных правил для оптики, сварок или кроссов.

`ConnectionMember` имеет стабильный ID и может иметь собственные metadata, например человекочитаемый номер, цвет, номер модуля/трубки или комментарий. Эти metadata не влияют на трассировку.

## Явный mapping

Mapping не бывает неявным.

Даже для очевидного случая:

```text
A:1  <-> B:1
A:2  <-> B:2
...
A:48 <-> B:48
```

в канонической модели существуют 48 явных `ConnectionMember`.

Причины:

- трассировка не требует отдельного режима `identity mapping`;
- перестановка любого member не меняет структуру модели;
- импорт из внешних источников не должен угадывать исключения;
- 48, 144 или 288 строк являются незначительным объёмом для БД.

Автоматическое создание последовательного mapping является удобством API/UI, а не другой формой хранения.

## Инварианты mapping

Для каждого `ConnectionMember`:

```text
1 <= point_a_member <= point_a.cardinality
1 <= point_b_member <= point_b.cardinality
```

В пределах одного `Connection`:

- `ConnectionMember.index` уникален;
- один `point_a_member` встречается не более одного раза;
- один `point_b_member` встречается не более одного раза;
- количество `ConnectionMember` равно `Connection.cardinality`.

Таким образом mapping одного Connection является взаимно-однозначным соответствием между двумя выбранными подмножествами members его точек.

Глобальное ограничение вида «member ConnectionPoint может участвовать только в одном Connection» **не вводится**. Одна точка пассивного проходного объекта должна иметь возможность участвовать во внешней и внутренней связи. Более строгие ограничения конкретных объектов могут появиться позднее как validation/capabilities, но не являются законом L1-ядра.

## Кабель как PhysicalObject

Кабель остаётся обычным `PhysicalObject`. Его тип, среда, категория и прочие характеристики являются metadata.

У простого кабеля есть две конечные ConnectionPoint и внутренняя Connection между ними.

### Одиночный кабель

```text
PhysicalObject CABLE-1
├── CP-A cardinality = 1
└── CP-B cardinality = 1

internal Connection
    CP-A:1 <-> CP-B:1
```

Подключение концов кабеля к другим физическим точкам задаётся отдельными Connection.

### 48-волоконный кабель

```text
PhysicalObject CABLE-48
├── CP-A cardinality = 48
└── CP-B cardinality = 48

internal Connection cardinality = 48
    A:1  <-> B:1
    A:2  <-> B:2
    ...
    A:48 <-> B:48
```

Отдельное волокно не становится `PhysicalObject` только потому, что оно индивидуально трассируется. В данном случае оно является `ConnectionMember` внутренней связи кабеля.

Если какой-либо вложенный компонент действительно требуется учитывать как самостоятельную физическую сущность с собственным жизненным циклом, inventory, metadata или ConnectionPoint, он по-прежнему может быть отдельным `PhysicalObject`.

## Сварка и перестановка

Сварка не требует специального класса. Например связь двух кабельных концов может содержать:

```text
Cable-A endpoint:17 <-> Cable-B endpoint:4
Cable-A endpoint:18 <-> Cable-B endpoint:7
Cable-A endpoint:19 <-> Cable-B endpoint:8
```

Это обычный `Connection` с `cardinality = 3` и тремя `ConnectionMember`. Metadata может классифицировать его как splice и хранить любые эксплуатационные атрибуты.

## Breakout

Один Connection связывает только две ConnectionPoint, поэтому breakout представляется несколькими связями.

Например объект с одной 12-канальной стороной и шестью двухканальными сторонами:

```text
PhysicalObject BREAKOUT

A   cardinality = 12
B1  cardinality = 2
B2  cardinality = 2
B3  cardinality = 2
B4  cardinality = 2
B5  cardinality = 2
B6  cardinality = 2
```

Внутри объекта существуют шесть Connection:

```text
A:1-2   <-> B1:1-2
A:3-4   <-> B2:1-2
A:5-6   <-> B3:1-2
A:7-8   <-> B4:1-2
A:9-10  <-> B5:1-2
A:11-12 <-> B6:1-2
```

Каждая строка выше разворачивается в два явных ConnectionMember. Специальная сущность `Breakout` не требуется.

## Трассировка

Для точной L1-трассировки элементарной вершиной становится не только ConnectionPoint, а адрес member:

```text
(ConnectionPoint, member_index)
```

`ConnectionMember` задаёт ребро между двумя такими адресами.

Поэтому трасса конкретного волокна может выглядеть так:

```text
CP-100:17
    -> Connection-1/member-17
CP-200:17
    -> Connection-2/member-3
CP-300:4
    -> ...
```

При агрегированной трассировке members могут быть схлопнуты до уровня ConnectionPoint, PhysicalObject или более высокого представления. Каноническая топология при этом не меняется.

## Что остаётся открытым

- правила валидации допустимой степени конкретных типов физических точек;
- модель физических маршрутов кабелей через промежуточные Location;
- история переподключений и временные состояния;
- API для массового создания последовательных mapping;
- импорт mapping из внешних источников.

Эти вопросы не меняют базовую модель `ConnectionPoint -> Connection -> ConnectionMember`.
