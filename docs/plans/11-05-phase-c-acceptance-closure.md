## Архитектурные границы и зависимости

- Каноническая топология остаётся источником физических фактов.
- По authoritative 09.6 `PhysicalObject` создаётся из обязательного базового
  шаблона; его комплектация дополняется module installations внутри объекта.
  Complete immutable `ObjectBlueprint` configuration superseded target-wise;
  immutable revisions и canonical materialization сохраняются.
  `Port Block` — только removed historical/superseded authoring
  model, не target prerequisite или library entity. Ни Blueprint, ни прежняя
  Port Block model не являются канонической топологией.
- `SavedMap`, `MapCableRoute`, derived Location frames,
  подписи и будущие кабельные направляющие — состояние представления. Оно не
  является источником канонической истины и не доказывает физические факты.
- Идентичность `PhysicalObject`, endpoint, `Connection`, `ConnectionMember`,
  `Cable` и `Blueprint` не зависит от подписей, координат, порядка или
  представления. Существующие неизменяемые версии остаются неизменяемыми.
- `C-COR-01` и `C-UX-08` описывают findings старого MapComposite workflow,
  superseded target architecture. Их старые remediation steps неактуальны;
  findings остаются `OPEN` до replacement Location-driven manual recheck.
- `C-CAP-01` — отдельный семантический пробел, а не расширение обычного
  1:1 patch-panel сценария. Новая каноническая сущность `Fanout/Splitter` не
  вводится.
- `C-UX-06` задаёт независимую геометрию размещения и поэтому проверяется до
  оценки аккуратной групповой компоновки; `C-UX-07` отдельно проверяет групповое
  перемещение.
- `C-UX-11` закрывается только в связи с новым group-move/route contract
  `P-UX-03D`; его нельзя автоматически считать решённым созданием общей
  кабельной направляющей из `C-UX-10`.
- `C-UX-10` добавляет общую кабельную направляющую только для представления.
  Она не является `PhysicalObject`, endpoint, `Connection`,
  `ConnectionMember`, `Cable` или каноническим физическим путём.
- `C-VIS-01` проверяется и на обычных пересечениях, и поверх общего участка
  кабелей; выделение одного `Cable` не включает соседние кабели в evidence.
- `C-UX-02` и `C-UX-09` допустимо закрывать в одном пользовательском сценарии
  создания `PhysicalObject`: пользователь выбирает компактный `Blueprint`, а
  штатный путь создания без `Blueprint` отсутствует.

Порядок не является новым планом работ: superseded MapComposite findings
ожидают replacement Location-driven recheck; остальные исправления
проверяются в порядке, удобном для конкретной ограниченной задачи, с учётом
зависимостей выше.

member-aware семантику. Достоверная модель требует многоканальную входную
ConnectionPoint, независимые member-позиции и точное соответствие members
передним портам. Canonical L1 предусматривает cardinality и ConnectionMember,
но текущий конструктор не предоставляет необходимого member-aware authoring:
существующий [C-CAP-01](#c-cap-01--cardinality-каналы-и-многоканальное-внешнее-подключение)
остаётся **OPEN**. Пользователь решил пока не создавать OP1 и не подменять
модель фиктивной коммутацией 1→24.

**Продолжение проверки.** Для R823 PP1 создан BaseTemplate с двумя панелями
по 24 ConnectionPoint и 24 внутренними связями 1:1. PhysicalObject
`ZU8-R823-PP1-to-821/03` успешно размещён на SavedMap в R823, U40. Проверка
семантики внутренней коммутации 1:1 выполнялась ранее; этот проход не является
новой независимой проверкой. Из того же шаблона создан и успешно размещён в
R821, U25 объект `ZU8-R821-PP3-to-R823/01`; повторное использование прошло
без новых замечаний.

Между PP1 и PP3 создан первый тестовый Cable с условно выбранными
соответствующими портами. Он первоначально отображался прямой линией;
аккуратное расположение требует отдельного редактирования MapCableRoute.
При 24 однотипных соединениях ручная прокладка каждого маршрута трудоёмка:
это дополнительное evidence для C-UX-10. Массовое сопоставление и создание
соединений C-CABLE-01 уже IMPLEMENTED, но полная массовая операция для этих
24 портов в этом проходе не подтверждена.

При редактировании шаблонов с десятками портов обнаружены трудности массового
именования и порядка (C-UX-12), компоновки страницы (C-UX-13) и чтения

порты и создал новые; это объясняет Added/Removed endpoint records и само по
себе не доказывает дефект сохранения идентичности.

**Не проверено.** Полная массовая операция для 24 портов, повторная ручная
проверка HV-01 и проверки открытых замечаний остаются незавершёнными.

**Неустановленная физическая трасса.** Исходный пример: два Cisco C9500 в

Известна логическая связь портов 27 двух Cisco через PortChannel с портами

достоверно не восстановлена; R825 может участвовать в отдельных трассах,

но не является установленным фактом реальной сети.

### C-CAP-01 — Cardinality, каналы и многоканальное внешнее подключение

**Исправить.** Библиотечное описание должно позволять для одного
`ConnectionPoint` задать `cardinality > 1` и связь конкретного канала входа с
конкретным выходом. При создании `PhysicalObject` это описание должно
материализоваться существующими каноническими примитивами: появляются
различимые `ConnectionMember`, связи между конкретными каналами и точное
L1 evidence/trace через конкретный канал. Канонические `Connection` и
`ConnectionMember` появляются в результате материализации, а не как прямое
действие редактирования `Blueprint`.

Дополнительно обязателен пользовательский сценарий внешнего подключения
многоканального `ConnectionPoint`: один многоканальный входной
`Cable`/`Connection` с несколькими `ConnectionMember` должен создаваться
через обычный пользовательский интерфейс и подключаться к соответствующим
внешним endpoint/member positions.

**Подтверждённая граница по текущему `main`.** Обычное создание физического
соединения сейчас ограничено `cardinality=1` и `member_index=1`. Поэтому
подтверждение `FANOUT-1x24` не может состоять из 24 фиктивных кабелей, 24
фиктивных входных ports, одного endpoint с прямыми связями без member identity
или presentation-only имитации. Нужен один многоканальный входной
`Cable`/`Connection` с несколькими `ConnectionMember`, созданный через UI.

**Граница `11-04`.** Это пробел библиотечного описания и материализации, не
утверждение отсутствия всей канонической модели L1. Physical endpoint не равен
отдельному физическому каналу; новая каноническая сущность `Fanout/Splitter` не
вводится. Конкретные schema, DTO/API, migration и внутренняя реализация не
фиксируются этим реестром.

**Исторический способ проверки (superseded):** в пустой части заново
создаваемого стенда через пользовательский интерфейс создать reusable
`Blueprint`/`Port Block` для `FANOUT-1x24` с одним входным
`ConnectionPoint` и 24 выходными позициями. В библиотечном описании задать
cardinality/member count входного endpoint и связь канала N с соответствующим
выходом. Создать один `PhysicalObject`, чтобы это описание материализовалось.
В карточке объекта проверить созданные канонические `ConnectionMember`, их
идентичности и внутренние связи.
Затем через пользовательский интерфейс создать один внешний многоканальный
входной `Cable`/`Connection` на incoming `ConnectionPoint` и присоединить его
каналы к внешним endpoint/member positions (а не создавать 24 отдельных ports или
кабелей). Выбрать отдельный `ConnectionMember`, выполнить его L1 trace,
открыть evidence и проверить, что выделен нужный канал и путь, а остальные
каналы не стали его evidence. Перезагрузка и повторное открытие объекта
должны сохранить результат.

**Закрыто, если.** Весь сценарий — библиотечное описание, cardinality > 1,

### HV-01-UX-01 visual corrective after manual recheck (2026-11-05)
