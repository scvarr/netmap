# 01.3 L2 — forwarding model

## Статус

Согласованная базовая концептуальная модель L2. Она фиксирует локальный forwarding context, связь с `NetworkInterface`, encapsulation и принцип вычисления сквозной L2-достижимости.

Точная схема хранения ingress/egress rules, FDB и protocol-specific state пока не фиксируется.

## Основной принцип

L2 не моделируется как глобальная сущность `VLAN`.

`VLAN ID` является частью представления Ethernet frame на конкретной границе, но сам по себе не идентифицирует L2-сеть.

Например:

```text
SW1 VLAN 100

SW2 VLAN 100
```

не означает, что между SW1 и SW2 существует L2-достижимость.

И наоборот, один сквозной L2-domain может проходить через преобразование tags:

```text
tag 100 -> forwarding context -> tag 200
```

Поэтому фиксируется инвариант:

```text
VLAN ID != L2 reachability domain
```

## L2ForwardingContext

Базовой локальной сущностью L2 является:

```text
L2ForwardingContext
    id
```

`L2ForwardingContext` означает локальный логический контекст, внутри которого устройство, bridge, virtual switch или другой forwarding mechanism способен пересылать Ethernet frames между присоединёнными интерфейсами.

Контекст локален. Он не обязан иметь глобально значимое имя или VLAN ID.

Пример:

```text
SW1

L2Context A
├── Gi1/0/1
├── Gi1/0/2
└── Gi1/0/48 [tag 100]

L2Context B
├── Gi1/0/3
└── Gi1/0/48 [tag 200]
```

`L2Context A` и `L2Context B` являются разными локальными forwarding context.

То, что один из них отображается оператору как `VLAN 100`, может храниться как конфигурационный факт/alias, но не определяет его идентичность.

## L2Binding

Связь `NetworkInterface` с локальным forwarding context задаётся явно.

Концептуально:

```text
L2Binding
    id
    interface_id
    forwarding_context_id
    external_representation
```

`external_representation` здесь является концептуальным обозначением. Его точная схема будет определена отдельно.

`L2Binding` отвечает на вопрос:

> Какое представление Ethernet frame на данном `NetworkInterface` соответствует этому `L2ForwardingContext`?

Один `NetworkInterface` может иметь несколько L2 bindings.

Это позволяет одному физическому или логическому интерфейсу одновременно переносить несколько независимых L2-context.

## Access, trunk и native VLAN

`access`, `trunk` и `native VLAN` не являются фундаментальными классами backend.

Они являются производными конфигурационными представлениями набора `L2Binding`.

### Access-подобное поведение

```text
Gi1/0/1

untagged <-> Context A
```

### Trunk-подобное поведение

```text
Gi1/0/48

tag 100 <-> Context A
tag 200 <-> Context B
tag 300 <-> Context C
```

### Native-VLAN-подобное поведение

```text
Gi1/0/48

untagged <-> Context A
tag 200  <-> Context B
tag 300  <-> Context C
```

Алгоритм не должен зависеть от строкового признака `mode=access` или `mode=trunk`. Истиной являются bindings и правила внешнего представления frame.

## Encapsulation

Encapsulation влияет на сетевую логику и поэтому не должна быть произвольной metadata.

На концептуальном уровне она рассматривается как упорядоченное представление frame на границе интерфейса.

Примеры:

```text
untagged
```

```text
[dot1q:100]
```

```text
[dot1ad:500, dot1q:100]
```

Последний случай позволяет естественно представить stacked encapsulation, например QinQ.

Фундаментальная модель не должна быть ограничена единственным полем `vlan_id`.

Точный формат `Encapsulation` будет определён в дочерней ветке после проверки требуемых операций трассировки и преобразования.

## Ingress и egress

`L2Binding` концептуально является соответствием между внешним представлением frame на интерфейсе и внутренним `L2ForwardingContext`.

Это соответствие может быть асимметричным.

Например:

```text
port A:
    ingress tag 100 -> Context X

port B:
    Context X -> egress tag 200
```

Поэтому модель не должна предполагать, что ingress match и egress encoding всегда одинаковы.

На текущем уровне фиксируется семантика, но не конкретные поля таблиц:

```text
external frame representation
            ↕
        L2Binding
            ↕
    L2ForwardingContext
```

## Internal attachment

Не каждый `L2Binding` обязан иметь внешнюю физическую encapsulation.

Например SVI:

```text
L2ForwardingContext A
        |
        | internal attachment
        v
NetworkInterface Vlan100
```

`Vlan100` может не иметь `InterfacePhysicalBinding`.

Это является нормальным способом перехода от L2 к будущей L3-модели:

```text
L2ForwardingContext
        |
NetworkInterface / SVI
        |
IPAddress / Prefix
        |
       L3
```

Точная L3-модель будет определена отдельно.

## Сквозная связь между локальными context

Рассмотрим trunk между двумя устройствами:

```text
SW1 Gi48 ============================== SW2 Gi48
     |                                      |
  tag 100                                tag 100
     |                                      |
 Context A                              Context X
```

`Context A` и `Context X` остаются разными canonical сущностями.

Их сквозная L2-достижимость выводится из последовательности фактов:

1. `Context A` связан через `L2Binding` с `(SW1 Gi48, tag 100)`;
2. интерфейс SW1 физически связан через L1 с интерфейсом SW2;
3. на проводе сохраняется соответствующее внешнее представление frame;
4. `(SW2 Gi48, tag 100)` связан через `L2Binding` с `Context X`.

Canonical backend не должен заранее объединять A и X в одну сущность только потому, что оператор считает их одной VLAN.

## L2ReachabilityDomain

Сквозной:

```text
L2ReachabilityDomain
```

является вычисляемой сущностью/проекцией.

Он отвечает на вопрос:

> Какие локальные L2 forwarding context в текущем состоянии сети образуют связную область L2-достижимости?

Пример:

```text
SW1 Context A
      |
   tag 100
      |
SW2 Context X
      |
   tag 200
      |
SW3 Context K
```

может дать производный результат:

```text
L2ReachabilityDomain R17
├── SW1 Context A
├── SW2 Context X
└── SW3 Context K
```

`R17` не является обязательным первичным фактом canonical storage.

Он может пересчитываться или кэшироваться как производная проекция.

## Configured и effective topology

L1-топология, L2-конфигурация и фактическое forwarding state являются разными слоями фактов.

Например STP может заблокировать один из физических путей:

```text
configured topology: link exists
effective L2 topology: path blocked
```

При этом:

- `Connection` в L1 не исчезает;
- `L2Binding` не обязан исчезать;
- меняется operational forwarding state.

Поэтому NetMap должен различать как минимум:

```text
configured L2 topology
effective L2 topology
```

Точное представление состояния будет определено отдельно.

## L2ForwardingState

Оперативное состояние не должно записываться в физический `Connection`.

Концептуально требуется отдельный факт:

```text
L2ForwardingState
    target
    state
    observed_at
    source
```

Примеры состояния могут включать:

```text
forwarding
blocked
disabled
unknown
```

Список состояний пока не фиксируется как окончательный enum.

`observed_at` и `source` принципиальны для будущих realtime adapters: operational state является наблюдаемым фактом, а не вечным свойством топологии.

## MAC и FDB

MAC address и forwarding database участвуют в алгоритме L2 forwarding и поэтому не должны быть произвольными metadata.

Будущая структурированная модель должна позволять выразить как минимум:

```text
MacAddress
MacBinding
FDBEntry
```

Концептуально:

```text
FDBEntry
    forwarding_context_id
    mac
    egress_interface
    observed_at
    source
```

Точная схема будет определена отдельно.

FDB является оперативным наблюдением. Она не определяет постоянную физическую или конфигурационную топологию.

## Known unicast, unknown unicast и broadcast

При packet/frame trace необходимо различать характер forwarding.

### Known unicast

Если destination MAC известен в актуальной FDB, forwarding может быть сужен до конкретного egress.

### Unknown unicast

Если destination MAC неизвестен, результатом может быть несколько допустимых forwarding branches согласно поведению context.

### Broadcast / multicast

Forwarding также может образовывать несколько ветвей.

Следовательно L2 trace не обязан всегда возвращать единственный линейный путь. Его результатом может быть дерево вариантов.

Точные правила multicast будут определены позднее и не фиксируются этой заметкой.

## Состояние L2 trace

Один `NetworkInterface` может одновременно нести несколько независимых L2-context.

Поэтому вершиной L2-трассировки недостаточно считать только `NetworkInterface`.

Минимальное внешнее состояние трассировки:

```text
(NetworkInterface, Encapsulation)
```

Например:

```text
(Gi1/0/48, [dot1q:100])
```

и:

```text
(Gi1/0/48, [dot1q:200])
```

являются разными состояниями L2 trace.

При внутреннем прохождении через устройство состояние может переходить в:

```text
L2ForwardingContext
```

а затем снова в `(NetworkInterface, Encapsulation)` на egress.

## Основные переходы L2 trace

Переход через boundary устройства:

```text
(NetworkInterface, Encapsulation)
        |
        | L2Binding
        v
L2ForwardingContext
```

Forwarding внутри локального context:

```text
L2ForwardingContext
        |
        | forwarding decision/state
        v
(NetworkInterface, Encapsulation)
```

Переход по физической среде:

```text
(NetworkInterface A, Encapsulation)
        |
        | InterfacePhysicalBinding
        | L1 Connection graph
        v
(NetworkInterface B, compatible Encapsulation)
```

Точная проверка совместимости representation на физическом переходе будет определена вместе с `Encapsulation`.

## Virtual switching

Модель не предполагает наличие физического switch.

Например Linux bridge:

```text
L2ForwardingContext
├── eth0
├── eth1
├── tap17
└── tap18
```

Virtual switch гипервизора:

```text
L2ForwardingContext
├── physical uplink
├── VM NIC A
└── VM NIC B
```

моделируются теми же сущностями.

Термин `switch` является удобной классификацией объекта/реализации, но не фундаментом L2-графа.

## Отношение к NetworkInterfaceRealization

`NetworkInterfaceRealization` и `L2Binding` отвечают на разные вопросы.

```text
NetworkInterfaceRealization:
    из каких lower interfaces реализован upper interface?

L2Binding:
    как interface участвует в конкретном L2 forwarding context?
```

Например subinterface может быть описан так:

```text
eth0.100
    |
    | realized over
    v
eth0
```

а его L2-семантика отдельно:

```text
eth0.100 / representation
    |
    | L2Binding
    v
L2ForwardingContext
```

Имя `.100` не является источником истины о VLAN tag.

## Canonical и derived data

### Canonical / observed facts

К canonical или наблюдаемым фактам относятся:

```text
NetworkInterface
L2ForwardingContext
L2Binding
Encapsulation rules
L2ForwardingState
MacAddress / MacBinding
FDBEntry
L1 topology
```

Статус canonical/observed зависит от источника конкретного факта.

### Derived data

Вычисляемыми являются как минимум:

```text
L2ReachabilityDomain
L2 trace result
configured/effective reachability projections
```

Производные результаты не должны становиться независимым источником истины, противоречащим исходным фактам.

## Инварианты

На текущем уровне фиксируются следующие инварианты.

1. `VLAN ID` не является идентичностью L2-domain.
2. `L2ForwardingContext` является локальной canonical сущностью.
3. Один `NetworkInterface` может иметь несколько `L2Binding`.
4. Encapsulation является структурированным сетевым фактом, а не произвольной metadata.
5. `access`, `trunk` и `native VLAN` не являются фундаментальными классами модели.
6. Ingress representation и egress representation не обязаны совпадать.
7. `L2Binding` может быть internal и не иметь физической encapsulation.
8. Сквозной `L2ReachabilityDomain` вычисляется из локальных context, bindings, L1-топологии и forwarding state.
9. Operational L2 state не изменяет L1 topology.
10. MAC/FDB должны иметь структурированную модель, если используются для трассировки.
11. L2 trace различает состояния `(NetworkInterface, Encapsulation)`.
12. L2 trace может возвращать несколько forwarding branches.
13. Physical switch не является обязательной сущностью L2-модели.
14. Имена интерфейсов и VLAN-like aliases не являются источником сетевой семантики.

## Открытые вопросы

Следующие вопросы намеренно не фиксируются этой заметкой:

- точная схема `L2Binding`;
- представление ingress match и egress encoding;
- формат `Encapsulation` и label stack;
- VLAN translation;
- QinQ и другие stacked encapsulations на уровне операций;
- LAG/LACP forwarding state;
- STP/MSTP/RSTP state и область его действия;
- MAC ownership и multiple MAC;
- FDB aging и достоверность наблюдений;
- multicast forwarding;
- VXLAN/EVPN и другие overlays;
- правила агрегации L2-проекции.

Эти вопросы должны уточняться отдельными дочерними ветками по мере проектирования и проверки на реальных сценариях.
