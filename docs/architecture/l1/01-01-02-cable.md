# 01.1.2 Cable domain architecture decision

## Статус

**FIXED — Cable.0, docs-only milestone.** Этот документ заменяет прежнюю
development-stage модель `Cable as PhysicalObject` во всех действующих
контрактах NetMap.

## Canonical model

`Connection` остаётся единственным canonical physical connectivity fact: это
недиректная связь ровно между двумя существующими `ConnectionPoint` и её
`ConnectionMember` mapping.

`Cable` — optional point-to-point domain entity, связанная ровно с одним
`Connection`. Поэтому один `Connection` имеет не более одного `Cable`, а один
`Cable` всегда имеет ровно один `Connection`:

```text
ConnectionPoint ── Connection ── ConnectionPoint
                       │ 0..1
                     Cable
```

Cable не является `PhysicalObject` и не владеет `ConnectionPoint`. У Cable нет
собственных endpoint points, internal `Connection`, `Blueprint`, Blueprint
provenance, geometry или `PhysicalObject` lifecycle. Концы Cable — это ровно
две точки его единственного Connection; отдельные connection points для Cable
не создаются.

Допустимы обе формы:

- direct physical `Connection` без Cable;
- cable-backed `Connection` с одним Cable.

Недопустимы orphan Cable без Connection и «отключённый с одного конца Cable».
Нельзя создавать Cable отдельно от Connection или оставлять Connection после
удаления его Cable.

## Atomic lifecycle

Операция cable-backed create атомарно создаёт `Connection` с полным
`ConnectionMember` mapping и его Cable в одной transaction. Ошибка любой части
не оставляет ни Cable, ни Connection.

Операция disconnect/delete cable-backed связи атомарно удаляет Cable вместе с
его Connection. Удаление direct Connection без Cable удаляет только Connection.
Ни Cable, ни Connection не удаляют участвующие `PhysicalObject` или их
`ConnectionPoint`.

Разрыв одного конца не является переходным состоянием canonical model: UI и
API либо не выполняют такую операцию, либо выполняют атомарное удаление всей
cable-backed связи.

## Boundaries

`MapCableRoute` — Saved Map presentation state. Он может ссылаться на Cable и
хранить map/view-specific waypoints, но не доказывает connectivity, не создаёт
Cable или Connection и не является их lifecycle. Одна canonical cable-backed
связь может иметь разные routes на разных Saved Maps; отсутствие route
допустимо.

Будущий `Cable Bundle` — также presentation-only grouping независимых Cable.
Он не создаёт connectivity, не объединяет Cable и не меняет их identity.

Object/Blueprint/Port Block semantics относятся к `PhysicalObject` и его
`ConnectionPoint`. Blueprint materialization может создавать точки и обычные
internal Connections внутри соответствующего PhysicalObject, но никогда не
создаёт Cable, Cable endpoints или Cable Blueprint provenance. Cable route
geometry вычисляется/сохраняется presentation-слоем и не входит в canonical
model.

Cable.3 is the next bounded metadata foundation. It plans only optional
`label`, optional `transport_category`, and optional `capacity_class` as
descriptive context for the point-to-point relation. Candidate transport
categories are `ETHERNET`, `FIBRE_CHANNEL`, `OTHER`, and `UNSPECIFIED/null`;
the enum name and null semantics remain implementation-time decisions.
Candidate capacity classes include `1G`, `10G`, `25G`, `40G`, `100G`, `8GFC`,
`16GFC`, `32GFC`, and `64GFC`.

`capacity_class` means rated/nominal Cable capacity. It is not interface
capability, configured rate, negotiated operational rate, or observed
throughput, and future resolvers must not infer those states from it. Cable.3
does not add Cat5e/Cat6/Cat6A, OM3/OM4/OS2, DAC/AOC, manufacturer, part number,
connector inventory, length, stock state, or splice/member decomposition. Cable
remains a relation over canonical connectivity, not physical inventory.

## Cutover policy

NetMap находится в pre-production. Старая Cable-as-PhysicalObject модель не
поддерживается и не является historical runtime contract. Никаких dual
read/write, compatibility aliases, legacy parsers или сохранения старых
development cable-data не требуется. Если существующие dev-данные
несовместимы, Cable.1 может применить destructive reset или новую миграцию;
уже applied Alembic revisions при этом не переписываются.

## Cable.1 structural-consumer boundary

Cable.1 обязан перевести не только canonical tables и mutation API, но и
current structural consumers старой Cable identity: catalog authoritative read,
`PhysicalObject` Details backend resolver, L1 projection semantics и
`MapCableRoute` storage/reference identity. Эти consumers должны получать
canonical `Cable` и выводить его two endpoints из one linked `Connection`; они
не могут распознавать или обходить Cable-`PhysicalObject` aggregate.

Такой cutover сохраняет bounded current behaviour через необходимые DTO/API и
frontend type adaptations, но не является redesign Object Details, новым Cable
product UX, новой route geometry или visual polish. Они остаются subsequent
work поверх уже новой canonical Cable model. Cable metadata foundation и
дальнейшие presentation capabilities также не могут возвращать legacy Cable
identity.

## Cable.3 label boundary

Cable.3 includes an optional mutable user-facing `label`. Label may be set,
changed or cleared; when absent, UI may use a deterministic technical fallback
that does not become the canonical user label automatically. Label writes are
Cable-specific and do not reuse PhysicalObject rename semantics. Changing the
label does not change Cable identity, linked Connection, endpoints,
`MapCableRoute` references, trace semantics or topology. No Cable Details
surface is introduced solely for this metadata capability.
