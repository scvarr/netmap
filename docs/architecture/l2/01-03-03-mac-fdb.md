# 01.3.3 MAC и FDB

## Статус

Согласованная минимальная модель MAC identity и forwarding database для `L2 Frame Trace`.

Эта заметка намеренно разделяет:

```text
кому MAC принадлежит
```

и:

```text
куда локальный forwarding context сейчас отправит frame на этот MAC
```

Эти факты имеют разную семантику, жизненный цикл и provenance.

Связанные заметки:

- [[architecture/l1/01-02-network-interface|01.2 NetworkInterface]];
- [[architecture/l2/01-03-l2|01.3 L2 — forwarding model]];
- [[architecture/l2/01-03-01-l2-binding-encapsulation|01.3.1 L2Binding и Encapsulation]];
- [[architecture/l2/01-03-02-l2-operational-state|01.3.2 L2 Operational State]];
- [[architecture/tracing/03-02-l2-trace|03.2 L2 Trace]].

## MacAddress

`MacAddress` является сетевым value object, а не человекочитаемой metadata.

Canonical значение должно быть независимо от текстового представления:

```text
aa:bb:cc:dd:ee:ff
AA-BB-CC-DD-EE-FF
aabb.ccdd.eeff
```

являются одним значением.

Конкретный способ хранения — integer, bytes или иной тип — пока не фиксируется.

Текстовое форматирование является presentation concern.

## Address class

Из значения MAC можно производно определить как минимум:

```text
unicast
multicast
broadcast
```

Это не требует отдельной пользовательской классификации.

Специальные/зарезервированные адресные диапазоны могут быть добавлены позднее, если реально влияют на trace semantics.

## MAC не обязан быть глобально уникальным фактом NetMap

NetMap не должен накладывать глобальное ограничение:

```text
one MAC -> one interface
```

Такая уникальность неверна для реальной инфраструктуры.

Возможны:

```text
VRRP/HSRP-like virtual MAC
active/standby systems
virtualization
MAC duplication/misconfiguration
migration
temporarily conflicting observations
```

Поэтому MAC value может участвовать в нескольких facts.

Конфликт или допустимость определяется контекстом и provenance, а не database UNIQUE по самому адресу.

## MacAssignment

Устойчивую или заявленную принадлежность MAC интерфейсу описывает:

```text
MacAssignment
    id
    mac
    interface_id
```

Семантика:

> этот MAC назначен, принадлежит или заявлен данным `NetworkInterface`.

Примеры:

```text
server eth0 -> 00:11:22:33:44:55
VM vNIC    -> 00:50:56:aa:bb:cc
SVI        -> 00:aa:bb:cc:dd:ee
```

`MacAssignment` может быть:

```text
configured
imported
discovered
observed
```

в зависимости от source/provenance.

Способ представления provenance будет унифицирован в ветке источников данных.

## MacAssignment не является FDB

Из:

```text
MAC X assigned to interface VM1/eth0
```

не следует, что промежуточный switch должен иметь:

```text
FDB X -> VM1/eth0
```

Промежуточный forwarding context знает только локальный next attachment, через который MAC был изучен или сконфигурирован.

Поэтому identity и forwarding information хранятся отдельно.

## Multiple MAC on one interface

Один `NetworkInterface` может иметь несколько MAC assignments.

Это требуется для:

```text
virtual MAC
secondary MAC
containers/VMs behind software interface
platform-specific interface behavior
```

Алгоритм не должен считать первый найденный MAC единственным.

## MAC as trace endpoint

Пользователь может задать target:

```text
destination MAC = X
```

Для нормализации запроса NetMap может использовать `MacAssignment`.

Возможные результаты:

```text
one known assignment
multiple assignments
no assignment with complete coverage
assignment data incomplete
```

Но `L2 Frame Trace` не обязан сначала разрешить destination MAC в конечный interface.

Он может трассировать frame по FDB до тех пор, пока:

- не достигнет известного target;
- не достигнет local/internal ownership;
- не упрётся в unknown/conflicting data.

## FDB semantic

FDB означает локальный forwarding fact:

> В `L2ForwardingContext C` frame с destination MAC X следует направлять через определённый `L2Binding`.

Концептуально:

```text
FDBEntry
    mac
    destination_binding_id
```

Context не дублируется логически, если он однозначно определяется через `L2Binding`, но на уровне хранения может быть денормализован для индексации/валидации.

Критический инвариант:

```text
FDB target = L2Binding
```

а не просто:

```text
FDB target = NetworkInterface
```

## Почему target — L2Binding

Один interface может участвовать в нескольких contexts:

```text
Gi1/0/48
├── Context A
├── Context B
└── Context C
```

Запись:

```text
MAC X -> Gi1/0/48
```

недостаточно точна для canonical forwarding model.

Правильная семантика:

```text
Context A / MAC X -> Binding(Gi1/0/48, Context A)
```

Таким образом FDB entry сразу находится в том же semantic graph, который использует `LOCAL_FORWARD`.

## FDB entry может указывать на logical interface

Switch может учить MAC на:

```text
physical interface
LAG
software bridge port
tunnel/overlay interface
internal logical attachment
```

Это не проблема, потому что target остаётся `L2Binding`.

Если binding ведёт на LAG, дальнейший `REALIZATION_DOWN` отдельно выбирает допустимые physical members.

FDB не должна преждевременно раскрывать LAG до физического порта, если само устройство форвардит через aggregate interface.

## FDBSet / FDBSnapshot

Отдельная `FDBEntry` не позволяет доказать отсутствие MAC.

Для frame trace нужен набор наблюдений с общей областью и temporal semantics.

Концептуально:

```text
FDBSnapshot
    id
    forwarding_context_id
    source
    observed_at
    completeness
```

и:

```text
FDBEntry
    snapshot_id
    mac
    destination_binding_id
    entry_kind?
```

`entry_kind` пока не является обязательным для core forwarding logic.

Он может хранить значения вроде:

```text
dynamic
static
local
remote
```

как structured evidence, если адаптер их знает.

Алгоритм не должен зависеть от vendor-specific строки kind без нормализованной semantics.

## Snapshot scope

Один snapshot относится к конкретному `L2ForwardingContext`.

Это делает completeness осмысленной:

```text
complete FDB for Context A at T
```

вместо неопределённого:

```text
кажется, мы получили какие-то MAC с устройства
```

Если source получает всю таблицу устройства одним запросом, adapter может разделить результат на context-scoped semantic snapshots с общим collection provenance.

## FDB completeness

Минимально:

```text
COMPLETE
PARTIAL
UNKNOWN
```

### COMPLETE

Источник утверждает, что набор содержит все FDB entries рассматриваемого context в рамках semantics snapshot.

Только `COMPLETE` позволяет делать отрицательный вывод:

```text
MAC X отсутствует
```

при условии достаточной freshness.

### PARTIAL

Известно, что получен только фрагмент таблицы.

Отсутствие MAC ничего не доказывает.

### UNKNOWN

Источник не способен подтвердить полноту.

Для отрицательного вывода трактуется так же осторожно, как partial.

## Freshness

FDB является быстро меняющимся operational state.

`observed_at` обязателен для snapshot.

Freshness policy не должна быть зашита одним глобальным TTL.

Она может зависеть от:

```text
source
poll interval
device type
query mode
declared FDB aging behavior
```

Конкретная политика будет определена в общей модели freshness.

Инвариант:

> stale FDB snapshot не должен бесшумно использоваться как current для exact effective frame trace.

## Aging

FDB entry может исчезнуть не потому, что topology изменилась, а потому что устройство забыло динамически изученный MAC.

NetMap не должен превращать FDB aging в удаление topology facts.

Исторические snapshots могут показать:

```text
T1: MAC X -> Binding A
T2: MAC X absent
T3: MAC X -> Binding A
```

при неизменной L1/L2 configuration topology.

Если source предоставляет age/remaining lifetime, эти данные могут сохраняться как observation metadata/evidence.

Core trace не обязан симулировать timer aging устройства.

## Static entries

Статическая FDB entry может быть долгоживущей, но forwarding semantics та же:

```text
(Context, MAC) -> L2Binding
```

Разница находится в provenance/configured-vs-observed lifecycle.

NetMap не требует отдельного topology primitive для static FDB.

Если configured static FDB понадобится для configured frame trace, тот же semantic entry может быть получен из configuration plane.

## Local MAC

Устройство может сообщать MAC как:

```text
local
self
cpu
router
```

Core model не должен использовать специальную строку `CPU` как магическое направление.

Предпочтительная нормализация:

1. представить локальную logical `NetworkInterface`, если она значима для модели;
2. связать её с context через internal `L2Binding`;
3. направить FDB entry на этот binding.

Пример:

```text
Context A
    |
    | FDB local MAC X
    v
internal binding
    |
SVI / control-plane NetworkInterface
```

Это естественно создаёт `LAYER_HANDOFF` к L3 или local delivery.

Если adapter не способен сопоставить vendor `CPU` с semantic binding, entry остаётся частично разрешённой evidence и exact trace может вернуть `UNKNOWN`.

## Remote MAC

В overlay/EVPN устройства могут иметь remote MAC, достижимый через tunnel/overlay interface.

Базовая FDB-модель уже позволяет:

```text
MAC X -> L2Binding(tunnel interface, Context A)
```

Дальнейшее раскрытие overlay tunnel пока не является задачей этой ветки.

Это хороший признак того, что FDB target должен быть semantic binding, а не physical port.

## Several entries for one MAC

В одном snapshot теоретически могут существовать несколько targets для одного MAC.

Причины:

```text
multi-destination forwarding
EVPN multihoming
transient state
duplicate/conflicting data
adapter normalization issue
```

Core model не должен запрещать это database constraint вида:

```text
UNIQUE(snapshot_id, mac)
```

вслепую.

Вместо этого FDB resolver определяет, являются ли несколько entries:

```text
семантически допустимым target set
```

или:

```text
конфликтом
```

До появления multi-destination semantics для обычного unicast несколько несовместимых targets должны сохранять ambiguity, а не приводить к случайному выбору.

## FDBResolution

Для destination MAC внутри current context resolver возвращает semantic result.

Минимально:

```text
FDBResolution

KNOWN
ABSENT_CONFIRMED
UNKNOWN
CONFLICTING
```

## KNOWN

Есть достаточно свежие и достоверные FDB facts, которые дают usable target binding или target set.

Пример:

```text
Context A
MAC X
    -> Binding B17
```

Frame trace продолжает `LOCAL_FORWARD` через B17 с учётом operational eligibility.

Если target binding сейчас `INELIGIBLE`, это отдельный forwarding gate; FDB entry от этого не переписывается.

## ABSENT_CONFIRMED

Условия:

```text
snapshot scope = current context
snapshot completeness = COMPLETE
snapshot fresh enough
MAC X not present
```

Только тогда можно сделать вывод:

```text
destination is confirmed unknown unicast
```

для этого context/snapshot.

Дальше применяется unknown-unicast behavior.

## UNKNOWN

Типичные случаи:

```text
no snapshot
PARTIAL snapshot
UNKNOWN completeness
stale snapshot
unresolved FDB target
source data unavailable
```

В этом состоянии engine не имеет права автоматически flood frame как unknown unicast.

Ведь MAC может существовать в реальной FDB, просто NetMap его не получил.

## CONFLICTING

Несколько достоверных observations дают несовместимые forwarding conclusions и precedence policy не разрешает конфликт.

Frame trace:

```text
verdict may become UNKNOWN
flag/reason = CONFLICTING_DATA
```

с evidence всех конфликтующих facts.

## Unknown unicast

`unknown unicast` является forwarding classification, а не синонимом:

```text
NetMap не нашёл MAC в базе
```

Правильная цепочка:

```text
destination is unicast
        +
FDBResolution = ABSENT_CONFIRMED
        =
confirmed unknown unicast
```

После этого context применяет configured/effective unknown-unicast forwarding policy.

До появления специальной policy модели нормальная bridge semantics может быть импортирована/нормализована адаптером как набор допустимых egress branches.

Core не должен безусловно предполагать flooding для любых устройств и contexts.

## Known unicast

Для обычного known unicast:

```text
FDBResolution = KNOWN
```

даёт candidate egress binding(s).

Далее каждая candidate branch проходит обычные gate:

```text
L2Binding eligibility
NetworkInterface eligibility
NetworkInterfaceRealization eligibility
egress encoding
L1 path
```

FDB не обходится вокруг operational state.

## Broadcast MAC

Broadcast destination определяется непосредственно из MAC value.

Для него FDB lookup не требуется.

Context применяет broadcast forwarding semantics и строит несколько egress branches.

FDB snapshots всё равно могут использоваться для source learning analysis, но это не часть destination trace.

## Multicast MAC

Multicast destination также определяется из MAC value.

Но точная multicast forwarding semantics не выводится из unicast FDB.

До появления:

```text
multicast forwarding database
IGMP snooping state
static multicast policy
```

exact multicast frame trace может оставаться ограниченным или `UNKNOWN`.

Не следует выдавать обычный unknown-unicast flood как замену multicast semantics.

## Source MAC

Destination MAC определяет forwarding decision, но source MAC тоже важен.

Он может использоваться для:

```text
FDB learning
source validation/security
LAG hashing
diagnostics
```

Эта ветка не симулирует learning update как side effect trace.

`L2 Frame Trace` по умолчанию является read-only semantic query и не должен изменять FDB state только потому, что виртуальный frame прошёл через context.

## Не симулировать learning как mutation

При trace:

```text
frame src=X enters Context A via Binding B
```

реальный switch мог бы изучить:

```text
X -> B
```

Но NetMap не должен автоматически записывать такой FDB entry в canonical/observed state.

Иначе диагностический запрос изменял бы модель сети.

Если понадобится what-if/simulation mode, он должен иметь отдельное ephemeral state.

## MAC move

Если последовательные snapshots показывают:

```text
T1: MAC X -> Binding A
T2: MAC X -> Binding B
```

это observation:

```text
MAC move
```

а не обязательное изменение `MacAssignment`.

Возможные причины:

```text
VM migration
host moved
LAG/overlay behavior
loop
spoofing
normal relearning
```

Интерпретация относится к diagnostics/analytics.

Базовая FDB model должна лишь сохранять temporal evidence.

## MAC assignment vs observed location

Следует различать:

```text
MacAssignment:
    "MAC X принадлежит VM1/eth0"

FDB:
    "SW3 Context A сейчас видит MAC X через Po12"
```

Оба факта могут быть одновременно истинны.

Это позволяет строить цепочку:

```text
known endpoint identity
        +
distributed FDB observations
        +
L2 topology
        =
explainable path toward endpoint
```

## FDB source / provenance

Snapshot и entries должны быть связаны с source.

Пример:

```text
source = switch SW3 adapter
observed_at = 2026-...
```

Если semantic snapshot построен путём нормализации нескольких vendor tables, provenance должен позволять показать исходные данные.

Например UI сможет объяснить:

```text
MAC 00:11:22:33:44:55
forwarded via Po10
because:
    Cisco MAC table entry dynamic
    VLAN-like local context ...
    collected at ...
```

## Snapshot identity and immutability

Исторический FDB snapshot логически является immutable observation.

Новый poll создаёт новое состояние/версию, а не переписывает смысл старого snapshot.

Физическая БД может оптимизировать хранение delta/history, но semantic API должен позволять ответить:

```text
что было известно на T?
```

и:

```text
какой snapshot использовал trace?
```

Это важно для воспроизводимости диагностики.

## Current view

Для обычного effective trace resolver выбирает наиболее подходящий current snapshot согласно:

```text
source precedence
freshness policy
coverage
query timestamp
```

`current` является derived view над observations, а не специальной вечной записью FDB.

## Query timestamp

В будущем trace request полезно поддерживать:

```text
at_time = now
```

или исторический:

```text
at_time = T
```

Тогда FDB resolver выбирает observations, релевантные этому времени.

Эта возможность не обязательна для первого backend, но модель snapshots не должна её запрещать.

## Forwarding evidence

Trace step для known unicast должен иметь evidence на FDB resolution.

Пример:

```text
Context A
    -- dst MAC X learned via Binding B17 -->
Binding B17
```

Evidence:

```text
snapshot_id
entry_id
source
observed_at
completeness
```

Для confirmed unknown unicast evidence также важно:

```text
snapshot_id
completeness = COMPLETE
observed_at
absence of MAC X
```

То есть отрицательный вывод тоже должен быть объяснимым.

## Индексация

Для frame trace критичен lookup:

```text
(context, mac) -> current FDB entries
```

Поэтому независимо от физической схемы БД должен существовать эффективный индекс/материализованное представление для такого запроса.

Это implementation constraint, а не изменение domain semantics.

## Инварианты

1. `MacAddress` является нормализованным value object.
2. Формат строки MAC не определяет идентичность.
3. MAC value не имеет глобального ограничения one-to-one с interface.
4. `MacAssignment` и `FDBEntry` являются разными фактами.
5. Один interface может иметь несколько `MacAssignment`.
6. `MacAssignment` не заменяет forwarding information промежуточных devices.
7. FDB entry имеет context-local semantics.
8. FDB target указывает на `L2Binding`, а не только на `NetworkInterface`.
9. FDB может указывать на physical, aggregate, internal или overlay interface через binding.
10. FDB observations имеют temporal semantics.
11. Отдельная FDB entry не доказывает отсутствие другого MAC.
12. Отрицательный FDB lookup требует scope-aware snapshot completeness.
13. `COMPLETE`, `PARTIAL` и `UNKNOWN` являются минимальными состояниями completeness snapshot.
14. `ABSENT_CONFIRMED` требует complete и sufficiently fresh snapshot.
15. Отсутствие MAC в partial/stale/unknown snapshot даёт `UNKNOWN`, а не unknown unicast.
16. `unknown unicast` — forwarding classification, а не отсутствие записи в NetMap.
17. Known FDB target всё равно проходит operational eligibility gates.
18. Broadcast не требует unicast FDB lookup.
19. Multicast не должен автоматически использовать unicast-FDB semantics.
20. Frame trace не мутирует FDB learning state.
21. MAC move между snapshots не обязан менять `MacAssignment`.
22. Snapshot provenance обязателен для объяснимости.
23. Исторический snapshot логически immutable.
24. Current FDB является derived view над observations.
25. Несколько несовместимых targets не разрешаются случайным выбором.

## Открытые вопросы

Следующие вещи откладываются до реального сценария:

- точная модель multicast forwarding / IGMP snooping;
- MAC mobility и EVPN-specific semantics;
- multi-destination unicast forwarding;
- precedence static vs dynamic entries конкретных платформ;
- global/shared FDB tables и способы нормализации их к local contexts;
- exact FDB freshness policies;
- source precedence/conflict resolution;
- историческое compact/delta storage;
- API `at_time`;
- what-if simulation с ephemeral learning state.

После этой ветки базовая семантика L2 достаточна для перехода к L3-модели. Остальные L2 детали можно добавлять по мере появления реальных сценариев, не меняя фундаментальные primitives.
