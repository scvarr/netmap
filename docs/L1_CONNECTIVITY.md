# L1 Connectivity — L1-CONTRACT-03

Этот документ определяет физический контракт L1 и критерии инженерной
готовности. **CURRENT** описывает доступную реализацию, **DECIDED TARGET** —
принятые требования, **OPEN** — нерешённые вопросы или работу в указанном
scope. Общие правила identity, ревизий, транзакций и evidence ведутся в
[ARCHITECTURE](ARCHITECTURE.md). Статусы и очередь — в
[PROJECT_STATE](PROJECT_STATE.md) и [BACKLOG](BACKLOG.md).

## Подтверждённые инварианты и источники

**CURRENT.** PhysicalObject представляет физическое оборудование.
ConnectionPoint — его физическое окончание с положительной cardinality.
NETWORK_PORT материализует point и отдельный NetworkInterface с
ownership/binding. CONNECTION_POINT может существовать без интерфейса.
Interface realization graph описывает состав интерфейсов. Физический путь
задают Connections и их members.

Connection — недирективная continuity между двумя различными points.
Каждый ConnectionMember задаёт пару индексов в диапазоне capacity своих
окончаний. Connection cardinality равна числу mappings, которое может
быть меньше capacity любого окончания. Внутри одного Connection уникальны
индекс mapping и оба endpoint members, поэтому разрешены subset и permutation.
DB uniqueness ограничена одним Connection. Exact trace проверяет, что
у member не более одного внешнего и одного внутреннего перехода.
Деление мощности, направленность и общая среда требуют собственного
физического контракта.
[Модели](../app/models.py) · [Repository](../app/repository.py).

Cable является отдельной canonical сущностью, связанной с одним Connection
уникальным обязательным `connection_id`. Connection между разными
PhysicalObjects представляет внешнюю связь. При отсутствии Cable такая
связь отображается как DIRECT_CONNECTION. Connection внутри одного объекта
представляет внутреннюю continuity. IDs Cable и Connection различны. Маркировка
и CableLabelHistory обслуживают Cable lifecycle отдельно от общего activity.

Resolver обходит canonical adjacency по точным адресам. Point trace и
групповая проверка возвращают явные refs к окончаниям, mappings и внешним
Cable. Object trace сохраняет отдельные ветви и циклы. REACHABLE для объекта
или интерфейса означает, что найден путь хотя бы для одной пары.
[Серверный контракт](#c-cap-01-04a--exact-member-trace-и-групповая-проверка).
[Point resolver](../app/resolver.py) · [Object resolver](../app/physical_object_l1_resolver.py) ·
[L1-AUDIT-01](audits/L1_READINESS_AUDIT.md).

## Принципиальные границы

**CURRENT — physical lifecycle.** Одиночный create между существующими
окончаниями адресует канал парой `ConnectionPoint.id` и `member_index`.
Операция создаёт один Cable, один Connection с cardinality=1 и один
ConnectionMember с выбранной парой. Для многоканального окончания индекс
обязателен. Для одноканальных окончаний сохраняется member=1 и прежняя
материализация свободного интерфейса в одноканальном сценарии.
Занятость внешнего member проверяется под locks ConnectionPoint, внутреннее
продолжение может использовать тот же member. Для многоканальной операции
требуется актуальный compatibility preview точной пары, включая ALLOW.
UNKNOWN требует явного согласия, DENY отклоняет запись.
Bulk create принимает от 1 до 256 упорядоченных пар members между двумя
объектами. Для многоканального
окончания индекс обязателен. Окончание может входить в несколько пар,
если адреса его members различны. Занятость проверяется пакетно под
блокировками уникальных ConnectionPoint в порядке UUID. Ответ сохраняет
порядок запроса и возвращает UUID Cable, Connection, обоих ConnectionPoint
и индексы обоих members. Bulk delete показывает
обозначения members обоих концов и проверяет
ожидаемые Cable, Connection, endings, members и labels всего набора под
locks. Конфликт отклоняет пакет целиком. Удаление Cable и его внешней
continuity атомарно освобождает occupancy и маркировку с сохранением её
истории. Освобождённую маркировку можно назначить вручную или получить из
шаблона повторно. Действующая политика уникальности проверяет активные Cable.
Повторное назначение добавляет новую запись истории. Internal continuity сохраняется.

Reconnect проверяет ожидаемое состояние и переносит один конец Cable на
точный адрес `ConnectionPoint.id + member_index` при любой допустимой
cardinality окончания. Сохраняются второй конец, Cable, Connection,
ConnectionMember, маркировка и её история.
Повтор после ошибки refresh выполняет только read согласно общему
[транзакционному контракту](ARCHITECTURE.md#транзакции-и-согласование-записей).
[Physical writes](../app/physical_connections.py).

## L1-CONTRACT-03 — DECIDED TARGET

### Назначение, canonical truth и готовность

L1 моделирует задокументированную физическую инфраструктуру и вычисляет
пути по canonical topology. **L1 CONNECTIVITY COMPLETE** требует полного
инженерного цикла для поддерживаемой физической модели: медные и
оптические каналы, authoring, lifecycle, серверную совместимость, пассивную
continuity оборудования и модулей, exact member trace и targeted инженерную
приёмку. Мониторинг, optical budget, negotiated state и discovery лежат
за пределами этого gate.

**L1 PRODUCT COMPLETE** дополнительно требует [IA-01–IA-06](UX_IA_CONTRACT.md#обязательность-и-связь-с-аудитом),
[независимых карт и workspace isolation](ARCHITECTURE.md#savedmap-варианты-и-spatial-isolation),
auth/ACL, sharing, activity, [переносимости определений](L1_REFERENCE_NETWORK.md#переносимые-определения),
обязательных PERF-002–005 по [backlog](BACKLOG.md#7-переносимость-производительность-и-стабилизация)
и итоговой [пользовательской приёмки](L1_REFERENCE_NETWORK.md#приёмка-и-evidence--будущий-запуск).
Оба уровня пока открыты. Зависимость L2/L3 от L1 описана в
[ARCHITECTURE](ARCHITECTURE.md#resolver-evidence-и-l1l2l3-boundaries).

### Физические каналы и Cable

Cardinality описывает независимо адресуемые members. RJ45 даёт одну
сетевую линию, оптика различает каждое физическое волокно. Проводники RJ45
отдельно не моделируются. Связи 2↔2 и 2↔1+1 сохраняют точные пары, где
2↔1+1 может описывать пассивную разводку или действительно независимые линии.
Специальная группирующая сущность или иерархия Fiber/Termination не требуется.
Один Cable документирует одну независимую физическую линию. Каждое волокно
имеет собственные Cable, Connection и один внешний ConnectionMember, который
связывает выбранные members двух окончаний. Обычная медная Ethernet-линия
также имеет один внешний mapping. Окончания с несколькими members сохраняют
существующую модель внутренней continuity.

### Пассивная инфраструктура

ODF, патч-панели, кроссы, муфты, сварки и разварки можно представлять пассивным
PhysicalObject с ConnectionPoint и явной парной internal continuity.
Существование объекта или совпадение типов не создаёт пути. Отдельная Splice
entity, редактор сварок, кассеты, измерения затухания и история сварочных работ
не обязательны для универсального L1. Специализированные расширения возможны
по отдельному контракту. PON splitter, CWDM/DWDM и другие специализированные
оптические механизмы требуют отдельного решения о семантике и обязательности.
Обычные парные Connections их не моделируют.

### Модульная конструкция

BaseTemplate задаёт базовую конструкцию, ModuleTemplate — библиотечное
определение компонента. ModuleInstallation входит в конфигурацию того же
PhysicalObject. Каждая установка имеет собственный UUID, а ключи её
окончаний и посадочных мест разрешаются в пределах установки.

В BaseTemplate новые MODULE_BAY создаются группой логических отсеков для
плат по количеству, панели и ModuleBayType. MODULE_PORT отображается на
панели как гнездо трансивера. Плата может определять физические окончания
и MODULE_PORT. Новые и публикуемые шаблоны модулей не могут содержать
MODULE_BAY, а шаблон трансивера не может содержать дочерние места.
Поддерживаемые цепочки новых установок — BaseTemplate → плата → трансивер
и BaseTemplate → трансивер. Новые вложенные MODULE_BAY и установка платы
в плату запрещены. Физический трансивер требует объявленного аппаратного
интерфейса и одного поддерживаемого окончания. Совместимость посадки
определяется по mount_kind и UUID типа из отдельного пользовательского справочника.

Размещённое место сохраняет название, ключ и X/Y. CAT-D-05 хранит
совместимость места и ModuleTemplate по виду и UUID. Само гнездо `MODULE_PORT`
не создаёт `NetworkInterface`. Явно объявленный аппаратный интерфейс
материализуется независимо от наличия трансивера (MOD-03A-1). Пустое гнездо
не создаёт `PortType`, `ConnectionPoint`, `InterfacePhysicalBinding` или адрес
для physical member mapping. Гнёзда установленной платы видны в конфигурации объекта.
Вложенное место адресуется парой UUID родителя и локального ключа.
Установки удаляются снизу вверх. При демонтаже платы проверяются зависимости
её окончаний и удаляемых интерфейсов, включая Cable и данные L2/L3.

В карточке PhysicalObject → «Физика» пустой `MODULE_PORT` отображается ромбом.
После физической установки на схеме карточки вместо ромба отображается
квадрат физического порта трансивера. Определение MODULE_PORT и UUID
родительского NetworkInterface сохраняются. FN-010-MAP-01 IMPLEMENTED,
ACCEPTED: L1-карта отображает корпуса установленных плат, пустые гнёзда
и физические трансиверы на соответствующих панелях. Производная проекция
сохраняет canonical kind, UUID и реальные окончания Cable; пустые гнёзда
не имеют ConnectionPoint или кабельных якорей.

Изменение опубликованной конструкции подчиняется L1-O6/O7.
Явная пассивная continuity плат доступна в C-CAP-MOD-01.
[Контракт определения и установки](#c-cap-mod-01--passive-moduletemplate-continuity).

**DECIDED TARGET.** Адаптер или линейная карта предоставляет свои интерфейсы. Сменный трансивер
реализует физическое окончание существующего родительского NetworkInterface.
Его ID сохраняется при допустимой замене, дублирующий interface не создаётся.
Конструкцию встроенного RJ45 задаёт основное оборудование. Для SFP/QSFP
свойства окончания задаёт трансивер в пределах возможностей оборудования.
Поддерживаемый аппаратный режим задаёт число интерфейсов, cardinality сама
по себе не определяет breakout.

**IMPLEMENTED · MOD-03B-1.** Два физических канала оптического окончания
явно связаны с одним существующим NetworkInterface. На схеме корпуса и
L1-карте одно физическое окончание занимает один квадрат независимо от числа
members. Имя типа и индекс member не задают направление канала.

**IMPLEMENTED · MOD-03B-2A.** L1-карта и карточка оборудования позволяют
подключить один Cable между выбранными members существующих окончаний.
Обозначения берутся из PortType, для нетипизированных окончаний используются
индексы. Занятые каналы видны в списках выбора, свободные каналы частично
занятого окончания доступны. Каждый Cable можно выбрать и удалить отдельно,
в том числе при общей геометрии маршрута. Маркер окончания остаётся общим
для всех его каналов на соответствующей панели FRONT или REAR.

**IMPLEMENTED · MOD-03B-2B.** В диалоге массового подключения выбирают по
одной панели каждого объекта. Отдельные каналы, группы, диапазоны окончаний
или каналов формируют две последовательности. Порядок окончаний и порядок
каналов внутри каждого окончания настраиваются независимо. Диапазон назначения
можно задать начальным каналом и числом выбранных позиций источника.

Групповой флажок окончания и действие «Выбрать все свободные» выделяют
свободные каналы в обоих режимах. В режиме «По позициям» диапазон и отдельное
действие «Выбрать все позиции» включают занятые позиции и показывают
конфликтные пары без сдвига остальных. Пару с занятым источником можно
исключить, для занятого назначения можно выбрать свободный канал или
исключить пару. Режим «По свободным каналам» уплотняет последовательности
до сопоставления. Оператор может переставлять назначения, исключать пары и
просматривать точные адреса, маркировку и совместимость всех оставшихся линий.
После записи обновляется проекция карты. При ошибке обновления повторяется
только чтение.

**IMPLEMENTED · MOD-03B-2C.** Reconnect переносит один конец существующей Cable
на точный адрес `ConnectionPoint.id + member_index`. Можно выбрать другой
свободный member того же окончания. Многоканальное назначение требует явного
выбора member. Диалог показывает оба адреса до и после переноса. Сохраняются
UUID Cable, Connection и ConnectionMember, маркировка с историей и
противоположный конец. Операция доступна для внешней Connection с одной
линией. При конфликте оператор перечитывает подключение и заново выбирает
назначение. После успешной записи повтор обновления карты выполняет только чтение.

### C-CAP-01-04A — exact member trace и групповая проверка

**IMPLEMENTED.** Запрос `POST /v1/traces/l1` принимает `from` и `to`.
Каждый адрес содержит UUID `point_id` и целый `member_index` от 1 до
cardinality, в том числе для свободных members. Переход содержит refs к обоим
ConnectionPoint, Connection, ConnectionMember и к Cable при наличии.
Роль перехода определяется владельцами окончаний. Внешняя связь, в том
числе DIRECT_CONNECTION, занимает внешнюю роль member. Внутренний переход
читается из materialized mappings внутри одного объекта и одной установки,
если точки принадлежат модулю. Binding к NetworkInterface
определяет активное окончание для данного member. Достигнутое активное
окончание завершает обход.

`POST /v1/traces/l1/group` принимает непустой список `expected_pairs` из
таких же пар. Источники уникальны среди источников, назначения уникальны
среди назначений, адреса внутри пары различны. Допускаются subset и
permutation. `results` сохраняет порядок запроса и возвращает для каждой
пары ожидаемые адреса, verdict, фактически подтверждённые hops и окончания.
`completeness` равна COMPLETE для всех доказанных пар, PARTIAL для части
и UNCONFIRMED при отсутствии доказанных пар. Резерв вне списка не участвует
в оценке.

Для недоказанной пары возвращаются UNKNOWN, доказанный участок и
`terminations` с указанием node ID и причины. Причины различают отсутствие
внешней связи (`MISSING_EXTERNAL_CONNECTION`), внутренней continuity или
любой коммутации, другое окончание и цикл. Одиночная трассировка и
объектный и интерфейсный поиск возвращают HTTP 409 `MODEL_ERROR` при
повреждении модели. В группе повреждение локализуется как
`INVALID_CANONICAL_DATA` в результате затронутой пары. Невалидные адреса и неоднозначные ожидаемые
mappings отклоняют запрос с HTTP 422. Evidence читается заново при каждом
запросе из согласованного snapshot canonical topology и не хранится.

### C-CAP-01-04B — пользовательская трассировка каналов

**IMPLEMENTED.** На карте откройте «Трассировка» → «Каналы» и укажите
оба объекта и канала. Адрес в списке содержит объект, панель, место
установки и модуль при наличии, порт и индекс канала. Свободные каналы
доступны для выбора. При полном совпадении подписей отображается
канонический идентификатор.

В режиме «Группа каналов» добавьте каждую ожидаемую пару вручную и нажмите
«Проверить группу». Можно проверять подмножество каналов и явно задавать
перестановку. Выбор строки показывает verdict и окончания этой пары,
а также подтверждённые участки, в том числе при UNKNOWN. При MODEL_ERROR
одиночная трассировка показывает ошибку запроса, при INVALID_CANONICAL_DATA
групповая проверка показывает причину окончания затронутой пары.
Изменение запроса и подтверждение сервером изменения коммутации снимают
прежний результат. Если обновление карты после записи завершилось ошибкой,
повтор выполняет только чтение. Адреса промежуточных окончаний дополняются
по каноническим ID. Если подпись недоступна, сохраняются UUID точки и
индекс канала, а подтверждённые участки остаются в результате.

Карта выделяет подтверждённые ConnectionMember, включая DIRECT_CONNECTION,
и Cable при наличии соответствующего evidence. FRONT и REAR временно
раскрываются для показанных участков. Пары и результаты существуют только
в открытой панели. В режиме «Интерфейсы» можно выбрать интерфейсы с прямыми
physical bindings и просмотреть каждую доказанную ветвь отдельно.
Вычисление выполняется сервером по canonical topology.

пройдены все десять сценариев. Задержка объектной трассировки TEST-ODF-02

### Справочники и совместимость

**CURRENT · CAT-D-SIMPLIFY-01.** PortType описывает физическое окончание,
например LC, SC или RJ45. Имя задаёт пользователь. Тип хранит UUID, среду,
цвет, lifecycle и упорядоченные уникальные обозначения members. Число
обозначений определяет cardinality.

Тип назначается окончанию BaseTemplate или ModuleTemplate по UUID.
Для NETWORK_PORT требуется один member. Многоканальный CONNECTION_POINT
получает cardinality своего типа. В BaseTemplate сохранённая cardinality
входит в immutable определение. Для исторического снимка без этого поля
действует семантика 1:1.

Структурные поля PortType (среда и members) и удаление
защищены при ссылках из черновиков, кандидатов и ревизий. Имя, описание,
цвет и правила совместимости можно редактировать у используемого типа.
Архивирование сохраняет существующие ссылки и запрещает новые назначения.

Cable — одна линия между двумя физическими окончаниями. Одно волокно —
одна Cable. Для одиночной и массовой коммутации выбирают окончания
и при необходимости задают маркировку. При переподключении сохраняются
UUID и маркировка линии.

Правила PortType:

- **Только такой же тип** разрешает только совпадающий UUID.
- **Пользовательская матрица** разрешает отмеченную пару двух матричных
  типов одной среды. Один упорядоченный ключ из двух UUID действует в
  обоих направлениях. Диагональ тоже требует отметки. Отметка сохраняется
  при переименовании и при смене режима. Смена режима может сделать её неактивной.
- **Не определено** даёт UNKNOWN при отсутствии явного запрета второй стороны.

В create, bulk и reconnect проверяются оба окончания каждой линии.
Достоверный PortType определяется по сохранённому mapping ConnectionPoint
в действующей ревизии базового шаблона или установленного модуля. У свободного
NetworkInterface без такого окончания и у ConnectionPoint без достоверной
привязки тип неизвестен.

- **DENY** блокирует запись при запрете правила или несовпадении сред
  окончаний. Явное противоречие имеет приоритет.
- **UNKNOWN** требует явного подтверждения, когда неизвестен тип окончания
  или не определено правило совместимости. Подтверждение открывается в диалоге NetMap.
- **ALLOW** требует двух достоверных PortType, совпадающей среды и разрешающего правила.

Для create и bulk используется POST с `?preview=true`. Для reconnect —
`POST /v1/cables/{cable_id}/reconnect/compatibility-preview`. Preview возвращает
общий вердикт и массив `pairs` с вердиктом и причинами для каждой пары.
Запись принимает `compatibility: {token, accept_unknown}`. Один токен покрывает
всю упорядоченную пачку, точные адреса её members, шаблон и ожидаемую
маркировку. Если хотя бы одно выбранное окончание многоканальное, токен
обязателен и при ALLOW. Сервер повторно читает физические зависимости под
блокировками, проверяет занятость и отклоняет устаревшее подтверждение.
Ни одна линия из запрещённой пачки не записывается. Токен действует в
текущем процессе backend. Workspace v17 переносит типы, матрицу и линии
по UUID. [Запуск на чистой тестовой БД](#чистая-тестовая-бд-для-cat-d-simplify-01).

Для reconnect токен связывает Cable, ожидаемые point ID и индексы обоих
members, UUID Connection и ConnectionMember, маркировку, сторону переноса,
точный адрес назначения и факты совместимости результирующей пары. При
многоканальном исходном или новом окончании preview обязателен даже при
ALLOW. Пропуск ожидаемых индексов допускается только если оба текущих
окончания и назначение одноканальные. Для одноканального назначения индекс
назначения можно опустить.

### Типы модульных портов и отсеков — CAT-D-05

`ModulePortType` описывает порт для трансивера (`MODULE_PORT`). Начальный
набор — SFP, SFP+, SFP28, SFP56, QSFP+, QSFP28, QSFP56, QSFP112, QSFP-DD,
OSFP и XFP. `ModuleBayType` описывает отсек для сетевой платы, линейной карты
или другого модуля (`MODULE_BAY`). Его начальный набор — PCIe x1/x4/x8/x16.
Оба справочника открыты. Переименование сохраняет UUID, архив сохраняет
действующие ссылки, а сервер отклоняет новые назначения архивного типа.

В `ModuleBay`, `ModuleTemplate` и собственных местах модуля (`module_places`)
поле `mount_kind` определяет единственную допустимую ссылку —
`module_port_type_id` или `module_bay_type_id`. У `ModuleBay` поля
`PLACED` и `LOGICAL` по-прежнему описывают размещение. Install и reconcile
проверяют совпадение и вида, и UUID. PCIe-карта может определять собственные
места SFP+. Исторические структурные трансиверы без окончаний по-прежнему
можно устанавливать и извлекать.

TX-LIB-01 разделяет библиотечные точки входа по `mount_kind`. Конструктор
трансиверов публикует ревизии того же `ModuleTemplate` с одним определением
физического окончания `CONNECTION_POINT`, ссылкой на `ModulePortType` и
ссылкой на `PortType`. Среда, число и обозначения физических members берутся из `PortType`.
Для оптической модели пользователь выбирает SM или MM в характеристиках
шаблона. Для медной модели поле неприменимо. Установка закрепляет
опубликованную ревизию и использует её характеристики. Совместимость Cable
определяется типами окончаний. Анализ оптического пути остаётся OPEN.
Скорость хранится в Мбит/с, дальность в метрах, длины волн TX/RX в нанометрах.
Дополнительные характеристики необязательны. Создание и публикация шаблона
не материализуют канонические сущности. Существующие установки закреплены
за своими ревизиями до отдельного reconcile.

Workspace v17 переносит необязательное поле `ModuleTemplateRevision.transceiver`
и определения черновиков и кандидатов. Старые ревизии без характеристик сохраняют
прежние данные и идентификаторы. Миграция `txlib01_specifications` добавляет
nullable-колонку и допускает откат до появления определений с характеристиками.

### Стабильные родительские интерфейсы MOD-03A-1

Необязательный UUID `hardware_interface_key` в `BaseTemplate.bays` или в
`ModuleTemplate.module_places` платы объявляет один аппаратный интерфейс
на месте `MODULE_PORT`. Ключ уникален в пределах определения. При создании
объекта или установке платы сервер выделяет UUID канонического `NetworkInterface`
с владельцем `PhysicalObject`. Конфигурация возвращает `network_interface_id`
на месте с объявлением. Для платы адрес места включает UUID родительской
установки и локальный `bay_key`.

Пустой порт не получает `ConnectionPoint` или `InterfacePhysicalBinding`.
Структурный трансивер сохраняет UUID родительского интерфейса при установке
и удалении. Прямое создание линии через такой интерфейс требует
`TRANSCEIVER_BINDING_REQUIRED`. `NETWORK_PORT` сохраняет собственную
материализацию с физическим окончанием.

Reconcile сохраняет ассоциацию при сохранении ключа, места и типа порта.
Изменение этих данных для уже материализованной конфигурации требует
вмешательства. Удаление платы удаляет её интерфейсы в той же транзакции после
проверки дочерних установок и зависимостей. Исторические конфигурации без
объявлений продолжают работать без создания новых интерфейсов.

Миграция `mod03a1_parent_interfaces` добавляет nullable-ключ мест
BaseTemplate и таблицу `hardware_interface_associations` с уникальными
ссылками на интерфейс и место в конфигурации. Workspace v17 переносит
объявления и `HardwareInterfaceAssociation` с сохранением UUID. До записи
проверяются владелец, адрес места и закреплённая ревизия.

### Физическая установка и кабель MOD-03A-2

Редакторы базового шаблона и платы назначают аппаратный интерфейс каждому
новому модульному порту. Назначение можно снять у выбранного порта. Для
существующих портов команды назначения всем или выделенным гнёздам создают
ключи только там, где их ещё нет. Ключ сохраняется при переименовании и
изменениях размещения. Копия гнезда с объявлением получает новый ключ.
Интерфейс материализуется при создании объекта или установке платы по
опубликованному определению.

Узкое исключение L1-O6 позволяет опубликовать ревизию того же BaseTemplate
с новыми ключами ранее необъявленных `MODULE_PORT`. Остальные элементы
физической структуры, включая существующие ключи, должны совпадать.
«Обновить совместимые объекты» отдельно добавляет интерфейсы в пустых
гнёздах существующего объекта с сохранением ранее выданных UUID.
Занятое гнездо или несогласованная конфигурация блокируют обновление всего
объекта. Пустое гнездо получает только интерфейс, владение и ассоциацию.

В карточке объекта на вкладке «Физика» можно установить совместимый
опубликованный трансивер с одним `CONNECTION_POINT` и одним физическим каналом.
Одной транзакцией создаются `ModuleInstallation`, `ConnectionPoint`,
`ModuleEndpointMapping` и `InterfacePhysicalBinding`. Привязка указывает на
member 1 и существующий аппаратный `NetworkInterface`. В mapping поле
`network_interface_id` остаётся пустым. UUID владельца, интерфейса и
закреплённая ревизия определяют происхождение установки.

На схеме карточки квадрат занимает место ромба. Кабель подключается из
таблицы физических портов с обычными проверками разъёма, среды и занятости.
Reconcile, меняющий физическое окончание или его привязку, и удаление
платы с дочерней установкой отклоняются. Весь объект с физическими трансиверами
можно удалить после устранения внешних зависимостей.

### Извлечение физического трансивера MOD-03C-1

Действие «Извлечь» в карточке оборудования требует подтверждения.
Для Simplex и Duplex в гнезде оборудования или установленной платы
демонтаж одной транзакцией удаляет установку, её ConnectionPoint,
ModuleEndpointMapping, InterfacePhysicalBinding каждого member и служебный
псевдоним окончания. Объект, родительская плата, гнездо, UUID аппаратного
NetworkInterface, его ассоциация, владение и зависимости L2/L3 сохраняются.

Кабель на любом member блокирует демонтаж. Ответ 409 содержит
`blocking_cables` с маркировкой при её наличии и адресами обоих окончаний.
В адрес входят имя объекта, путь Location, панель и сторона, имя окончания
и пользовательское обозначение member. Идентификаторы Cable, Connection,
ConnectionMember, объектов и окончаний, а также индексы members доступны
в диагностических данных. В карточке кабель без маркировки определяется по
паре адресов, а обозначение единственного канала опускается. Другие зависимости
окончания и несогласованные mapping, bindings или владение также блокируют
операцию. Проверки выполняются под блокировкой окончания, общей с созданием
и reconnect Cable.

После обновления карточка и L1-карта показывают пустое гнездо без окончания
и кабельного якоря. Повтор обновления выполняет только чтение. При повторной
установке новые физические сущности привязываются к прежнему NetworkInterface.

### Замена физического трансивера без внешней коммутации MOD-03C-2

Действие «Заменить» в карточке оборудования открывает диалог выбора
совместимого опубликованного трансивера. Диалог показывает текущую установку,
изменение PortType и числа каналов и подтверждает сохранение аппаратного
интерфейса. Новая опубликованная ревизия того же шаблона допустима.
Выбор уже установленной ревизии оставляет конфигурацию без изменений.

Сервер сверяет подтверждённую установку, гнездо, аппаратный интерфейс и
выбранную опубликованную ревизию. В одной транзакции он проверяет зависимости
по правилам MOD-03C-1, удаляет старые физические сущности и устанавливает
новые в то же гнездо. UUID NetworkInterface, ассоциация, владение и L2/L3
сохраняются. При наличии Cable сервер возвращает адреса обоих окончаний
для согласования переноса по MOD-03C-3. Ошибка создания нового окончания
или привязок откатывает все изменения транзакции.

После успеха карточка и проекция L1 обновляются. Повтор обновления выполняет
только чтение.

### Замена физического трансивера с коммутацией MOD-03C-3

Действие «Переподключить» в диалоге замены открывает сопоставление всех
подключённых Cable. Для каждой линии карточка показывает маркировку при
наличии, оба текущих адреса и выбор нового канала по его пользовательскому
имени. Каждый Cable получает ровно одно явное назначение, каждый новый
канал используется не более одного раза. Частичная коммутация, subset и
перестановка допустимы. Если каналов недостаточно, освободите лишние
подключения штатным отключением или переподключением. При выборе другой
ревизии сопоставление и подтверждение сбрасываются.

Диалог отправляет полное `cable_assignments` в существующий endpoint замены
с `?preview=true`. Сервер проверяет демонтаж и совместимость всех
результирующих пар по правилам reconnect. ALLOW требует preview, UNKNOWN
также требует явного согласия, DENY блокирует замену целиком. Запись
принимает `compatibility: {token, accept_unknown}`. Токен привязан к
конфигурации, установке и ревизиям, Cable, Connection, ConnectionMember,
точным адресам, сопоставлению и актуальным входам проверки совместимости.
Preview откатывает транзакцию. После конфликта требуется новый preview.

При подтверждении сервер меняет только адрес локальной стороны каждой
линии. UUID Cable, Connection и ConnectionMember, маркировка и
противоположные окончания сохраняются. Старые установка и связанные
физические сущности заменяются одной транзакцией с сохранением
аппаратного NetworkInterface и его зависимостей. Карточка и L1-проекция
заново читают точные окончания и якоря из canonical topology.

### Двухканальная оптическая установка MOD-03B-1

Совместимое гнездо MODULE_PORT шасси или установленной платы принимает
оптический трансивер с одним определением CONNECTION_POINT и двумя members
в закреплённом PortType. Установка атомарно создаёт один ModuleInstallation,
один ConnectionPoint с cardinality=2, один ModuleEndpointMapping и два
InterfacePhysicalBinding для members 1 и 2. Обе привязки указывают на тот же
существующий NetworkInterface. Поле network_interface_id в mapping пустое,
ownership и HardwareInterfaceAssociation сохраняются. При установке
Connection, Cable и внутренняя continuity отсутствуют.

На FRONT и REAR карточка и L1-карта отображают один квадрат на окончание,
с существующей обводкой и цветом PortType. Подробности показывают количество
и обозначения members. Независимые Cable могут подходить к тому же маркеру,
каждая со своей ссылкой на point/member. Одиночное и массовое создание
поддерживают выбор точных members. Reconnect также позволяет выбрать свободный
member многоканального окончания, в том числе при переносе внутри одного
окончания.

Workspace v17 переносит установку, mapping и все bindings с сохранением UUID.
До записи импорт проверяет совпадение места и закреплённых ревизий, владельца,
кардинальность и точный набор привязок к объявленному интерфейсу.

### Исторические установки и reconcile MOD-02A/B

MOD-02A реализовал рекурсивные деревья установок с адресацией дочернего
места по UUID родительской установки и локальному ключу. MOD-ASSEMBLY-01
ограничил структуру новых установок описанными выше цепочками.
Прежние опубликованные ревизии, размещённые отсеки PLACED и деревья
установок сохраняются. Ограничения MOD-ASSEMBLY-01 действуют при авторинге
и установке через API. Импорт Workspace v17, чтение и reconcile
применяют правила исторических ревизий.

MOD-02B проверяет вложенную установку по месту в закреплённой ревизии её
непосредственного родителя. При обновлении родителя занятые совместимые ключи
сохраняются. Остальные дети перемещаются целыми поддеревьями только при
единственном совместимом назначении свободных мест. Отсутствие назначения
или неоднозначность требуют вмешательства. UUID установок, родительские
ссылки и закреплённые ревизии потомков сохраняются.

Проверка кандидата и повторная проверка под блокировкой используют одинаковые
правила размещения. Обновление ревизии и перенос её детей входят в одну
транзакцию. Сохраняемые окончания и mappings удерживают UUID, подключения,
Cable и bindings. Производная геометрия вложенных модулей пересчитывается
относительно родительского места с учётом ориентации на каждом уровне.
Ручная компоновка корневой установки сохраняется.

BaseTemplate reconcile проверяет всё дерево и допускает безопасное обновление
метаданных при наличии вложенных установок. Опубликованная физическая
структура BaseTemplate остаётся неизменяемой.

Workspace JSON v17 переносит UUID установок, родительские ссылки, закреплённые
ревизии, canonical endpoints и mappings. Пакет проверяется до записи. Формат
также переносит оба справочника, виды и ссылки, включая ссылки
на архивные записи. Проверка пакета выполняется до записи данных.

#### Переход существующей базы

Alembic применяет опубликованную `catd05_module_port_types`, затем
`catd05_split_mount_types`. Первый шаг преобразует точные строковые значения
в UUID и останавливается при коллизии имён. На базе с уже зарегистрированной
первой ревизией Alembic начинает со второго шага. Второй шаг классифицирует
начальный набор по известным UUID и сохраняет текущие имена и статус.
Для остальных записей требуется операторское сопоставление
`NETMAP_CAT_D_05_MOUNT_KINDS` в виде JSON-объекта
`{"<uuid-порта>": "MODULE_PORT", "<uuid-отсека>": "MODULE_BAY"}`. Диагностика перечисляет
UUID и текущие имена записей, которым нужно назначить вид. Это решение
применяется ко всем ссылкам на UUID. При неоднозначном значении без
сопоставления транзакция откатывается.

Остановите backend, соберите образ и выполните миграцию в контейнере,
передав сопоставление из текущей оболочки, если оно требуется.

```sh
docker compose stop backend
docker compose build backend
docker compose run --rm -e NETMAP_CAT_D_05_MOUNT_KINDS backend alembic upgrade head
docker compose up -d
```

Переход сохраняет UUID справочников, шаблонов, ревизий, определений и
установок, а также окончания, интерфейсы и кабели. Серверные черновики и
снимки review переводятся на новый контракт. Для неопубликованного
кандидата после перехода требуется повторная проверка.

## Принятые решения L1-O1–L1-O10 — DECIDED

| Решение | Действующий смысл |
|---|---|
| L1-O1 | Канал — независимо подключаемая медная линия или оптическое волокно. Число каналов задаётся данными. |
| L1-O2 | Общие правила internal/external mapping: прямой, обратный или заданный порядок, preview, ручная коррекция, subset, occupancy и атомарная запись. |
| L1-O3 | В обычной модели один member допускает максимум одно внешнее и одно внутреннее соединение. Конфликт сохраняет прежние связи. |
| L1-O4 | Парные mappings не моделируют splitter. Специализированная оптика имеет отдельный OPEN scope. |
| L1-O5 | Каждое документированное волокно имеет собственный Cable. Несколько Cable могут идти одним геометрическим маршрутом. Совпадения маршрутов и маркировки не объединяют canonical topology. Метки вроде `CAB01/1/24` являются пользовательским текстом и не создают резервные волокна или сущность оболочки. Настоящая многоконцевая MPO→LC сборка остаётся за пределами обязательного базового L1. Её identity, lifecycle и включение в будущий scope остаются OPEN. Фиктивные endpoints, Cable и connections недопустимы. |
| L1-O6 | Переделка базовой конструкции требует нового BaseTemplate и нового PhysicalObject. Единственное исключение для физической структуры той же модели допускает добавление `hardware_interface_key` ранее необъявленным `MODULE_PORT` через новую ревизию. Существующие объекты получают интерфейсы для пустых гнёзд через явный reconcile. Внутренние instance overrides не допускаются. Описание и presentation исправляются отдельно. |
| L1-O7 | Изменение физической конструкции модуля требует нового ModuleTemplate. Это правило распространяется на опубликованную пассивную разводку, определённую явными member mappings. Новые установки ограничены MOD-ASSEMBLY-01, исторические деревья сохраняются. |
| L1-O8 | Активные порты завершают L1 trace. Пассивное продолжение требует явной continuity. Тип устройства, active conversion и L2 forwarding не создают физический transit. |
| L1-O9 | Переделка базового оборудования создаёт новую identity. Внешняя перекоммутация сохраняет identity оборудования. При допустимой замене трансивера сохраняется родительский NetworkInterface. Автоматический перенос старых подключений запрещён. Исправление ошибочных данных имеет отдельный lifecycle. |
| L1-O10 | Exact canonical evidence каждого member включает разрешимые refs к points, Connection, ConnectionMember и внешнему Cable. Группа оценивает members независимо и сверяет полноту с явными ожидаемыми mappings. Резерв сам по себе не ошибка. REACHABLE означает документированный путь и не подтверждает физическое измерение, исправность или Ethernet link. |

## Обязательные проверочные сценарии

Инженерная приёмка использует небольшие targeted fixtures для каждого контракта.

- Patch cord и цепь пассивных объектов: точные hops, после разрыва UNKNOWN.
  Активный объект не добавляет transit.
- Rear-N → отдельные front points с независимыми внешними Cable, включая
  rear-24: exact member evidence после reload, permutation/subset, резерв, отсутствие пути
  к чужим members и полный групповой результат по ожидаемым парам.
- Внешний lifecycle: актуальный preview, create/edit/disconnect, занятый member
  отклоняет всю запись, свободный member того же point доступен, disconnect
  сохраняет внутреннюю continuity. Отдельно проверяются три исхода compatibility.
- Для будущих контрактов: passive continuity из явных mappings и независимый
  trace обоих волокон LC Duplex с явным binding к одному интерфейсу.
- Допустимый reconcile сохраняет identity и зависимости, конфликт отклоняется
  атомарно. Точный lifecycle для ещё открытых операций проверяется после
  согласования их контракта.

## C-CAP-01-01 — definitions и materialization

**CURRENT.** BaseTemplate хранит положительную `cardinality` (по умолчанию 1,
NETWORK_PORT только 1, верхний технический предел — PostgreSQL int) и явные пары `from_member_index`/`to_member_index`
в `member_mappings` относительно `from_slot_key`/`to_slot_key`. Порядок пар не задаёт связность. Повторная
внутренняя занятость запрещена во всём definition. Материализация атомарно
создаёт points и exact internal Connections/Members без Cable. При чтении
сохранённых исторических 1:1 definitions отсутствие mapping означает 1→1.
Некорректная повторная occupancy даёт `INTERNAL_MEMBER_OCCUPANCY` при чтении,
review, reconcile, materialization и import, без ремонта или частичной записи.

Draft check и publish независимо отклоняют изменение физической сигнатуры
с `PHYSICAL_STRUCTURE_IMMUTABLE`, даже без экземпляров:
endpoint keys/kind/cardinality/port_type_id, internal mappings и module place keys/kind/
module_port_type_id. Геометрия, цвет и подписи не входят в сигнатуру. API и archive
roundtrip сохраняют multichannel definitions. Reconcile сохраняет retained IDs
и разводку, без provenance
не удаляет существующие Connections и не переписывает capacity, допустимые
добавления internal links ограничены 1:1. ModuleTemplate materialization
берёт cardinality точки из PortType, а NETWORK_PORT получает прежний binding
к member 1. Review и publish ModuleTemplate отклоняют смену PortType у
сохранённого endpoint. Reconcile сравнивает PortType с закреплённой ревизией.
[Materialization](../app/hardware_catalog.py) · [Reconcile](../app/object_reconciliation.py).

## C-CAP-01-03A — BaseTemplate member mappings authoring

**IMPLEMENTED.** В «Порты и внутренние связи» BaseTemplate две панели выбора
A/B подготавливают точные пары «стабильный ключ окончания + индекс канала».
Один internal link содержит все пары между этими окончаниями. Внутренняя
занятость проверяется по каждому адресу во всей конструкции. Применение
обновляет черновик целиком, а удаление последней пары убирает определение link.

В новом шаблоне и копии опубликованной ревизии доступны точечное и массовое
сопоставление, подмножества и перестановки. Локальный draft, серверный draft
и опубликованная ревизия сохраняют точные пары. В опубликованной конструкции
разводка доступна для просмотра, а допустимые изменения оформления проходят
обычные этапы save, review и publish. Для изменения разводки создаётся копия.

[Управление парами и ограничения операций](UX_IA_CONTRACT.md#разводка-каналов-basetemplate).

## C-CAP-01-03B — ModuleTemplate member mappings authoring

**IMPLEMENTED.** В новой плате и в копии опубликованной ревизии действие
«Внутренние связи» позволяет выбирать собственные пассивные окончания и

## C-CAP-MOD-01 — Passive ModuleTemplate continuity

**IMPLEMENTED.** В API определения платы (`MODULE_BAY`) массив
`internal_links` задаёт пары собственных пассивных окончаний
`from_endpoint_key` и `to_endpoint_key`. В каждом link непустой массив
`member_mappings` перечисляет явные пары `from_member_index` и
`to_member_index`. Индексы начинаются с 1, верхняя граница берётся из PortType
соответствующего окончания. Поддерживаются 1:1, subset и permutation.
Каждый адрес «ключ окончания + индекс» используется во внутренней разводке
не более одного раза. NETWORK_PORT, посадочные места и трансиверы не создают
пассивного транзита.

Draft сохраняет определение и проверяет допустимость mappings. Review и
publish независимо сравнивают разводку с опубликованным источником.
Порядок links и пар и направление записи пары не задают связность.
Для изменения разводки нужно создать новый ModuleTemplate.
[Графический редактор и копирование](#c-cap-01-03b--moduletemplate-member-mappings-authoring).

При установке каждое определение link создаёт собственный canonical Connection
с точными ConnectionMember и без Cable. Внешняя коммутация использует
независимую occupancy. L1Resolver проходит только по созданным парам.
Изменение layout и допустимый reconcile сохраняют IDs установки, points,
Connections и members. Демонтаж сначала проверяет все зависимости, затем
удаляет только собственную внутреннюю разводку и окончания. Внешние
зависимости блокируют операцию, Cable сохраняется.

Workspace сохраняет определения, черновики, кандидатов, закреплённые
ревизии и canonical mappings со всеми IDs. Импорт проверяет, что разводка
каждой установки совпадает с её ревизией, и атомарно отклоняет расхождения.

### Чистая тестовая БД для CAT-D-SIMPLIFY-01

Вперёд применяется ревизия `catd_end_types_01`. На чистой БД миграции
добавляют RJ45, LC Simplex, LC Duplex, SC и 12-канальное оптическое окончание.
Для первых четырёх включён режим «Только такой же тип», для 12-канального —
«Не определено». Режим волокна задаётся в шаблоне модели трансивера.

Чтобы поднять чистый тестовый экземпляр, используйте новый Compose-проект.
Пример предполагает локальный стек `netmap`, стандартный `compose.yaml` и
встроенную БД Compose. Проверьте, что имя нового проекта и его том
`netmap-catd-end-types-fresh_postgres_data` ещё не заняты. Проверьте также, что
`DATABASE_URL` в окружении и `.env` не указывает на внешнюю БД.
Если на 5173 или 8000 работает старый стек, остановите его. Команда `stop`
сохраняет контейнеры и данные.

```powershell
docker compose -f compose.yaml -p netmap stop
docker compose -f compose.yaml -p netmap-catd-end-types-fresh up -d --build --wait
docker compose -f compose.yaml -p netmap-catd-end-types-fresh exec backend alembic current
```

Убедитесь, что текущая ревизия — `catd_end_types_01 (head)`, и откройте
[NetMap на 5173](http://localhost:5173). Для повторного чистого запуска
используйте другое свободное имя проекта. Импорт принимает Workspace v17
в пустой набор данных. Стартовые справочники считаются данными, поэтому
сброс для импорта выполняется пользователем отдельно через Workspace.

Для изолированного прогона серверных тестов используйте новое имя проекта
и `compose.test.yaml`. В нём PostgreSQL работает с tmpfs. Команды ниже
запускают тесты только в изолированной БД `netmap_test`.

```powershell
docker compose -f compose.test.yaml -p netmap-catd-end-types-test run --build --rm test-runner pytest -q tests/test_physical_compatibility_e2e.py tests/test_cable_lines_e2e.py tests/test_transceiver_library.py tests/test_transceiver_binding.py tests/test_workspace_portability.py
```
