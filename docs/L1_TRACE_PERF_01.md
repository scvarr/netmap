## Стенд и результаты

Изолированный Compose-проект с PostgreSQL 17.6 на tmpfs и Python 3.13.7
из штатных Docker-образов. Docker Desktop выделял 14 CPU и 7,8 GiB RAM.
База исходной реализации — `e12b0549a2e285a64530b54c9bbcc0bace3ef960`.
Обе реализации читали одни и те же записи с теми же UUID. Основная БД
NetMap в измерениях не участвовала.

В объектном сценарии две одинаковые кассеты установлены в одном объекте.
На каждой кассете IN-1/OUT-1 используют Duplex с перестановкой 1→2 и 2→1.
IN-2/OUT-2 имеют 12 каналов с разводкой 1→1 … 10→10, каналы 11 и 12
свободны. Только первая кассета подключена внешней цепочкой с обоих
Duplex-окончаний. В увеличенном сценарии IN-2/OUT-2 имеют 24 канала с
22 внутренними mappings. Интерфейсные сценарии используют цепь через
пассивный объект, 12 или 24 bindings на каждом конце, перестановку
каналов и два пути реализации к одним и тем же bindings источника.

Все значения времени указаны в миллисекундах. TTFB и полное HTTP-время
измерены отдельным запросом через Uvicorn по loopback внутри контейнера.
Счётчики и разбивка времени сняты с отдельного инструментированного
запроса через FastAPI TestClient. Каждая строка представляет один замер
до и один после, поэтому небольшие различия между сценариями могут
зависеть от прогрева и нагрузки хоста.

## Механизм и ограничения

Главный источник задержки — повторные проверки тех же адресов и чтение их
смежности и привязок при полном обходе для каждой ожидаемой пары. Объектная
трассировка дополнительно повторяла обход источников для поиска циклов.

Теперь обе составные трассировки используют один возобновляемый обход L1
на уникальный исходный `PointMember`. Обход останавливается на уже
доказанной цели и продолжает ту же очередь, если следующая цель требует
дальнейшего поиска. В объектном запросе поиск циклов завершает уже начатые
обходы после построения ветвей. Проверка кандидатов остаётся в прежнем
порядке. Несколько реализаций интерфейса могут обращаться к одному обходу,
при этом каждая сохраняет собственную ветвь, если её связность доказана.

Исходные адреса загружаются пачками до 128. Каждое новое посещённое окончание
добавляется в общий для запроса memo смежности и активности. При ошибке
пакетной проверки чтение повторяется по адресам в порядке фактического
обхода, чтобы расположение повреждения определяло прежний момент
`MODEL_ERROR`. Коррелированный подсчёт members ограничен найденными
Connection. Объектный и интерфейсный API читают один snapshot
`REPEATABLE READ`. Следующий запрос получает новый снимок. Производительность
по-прежнему зависит от длины достижимых путей, числа проверяемых пар и
объёма выдаваемых ветвей. Лимит на выдачу результатов не вводился.

Четыре нагрузочных и одиннадцать контрольных запросов дали одинаковые
HTTP-статусы и полные JSON-артефакты. Сравнение сохраняет порядок массивов,
в том числе кандидатов, ветвей, направленных переходов, evidence, циклов и
причин завершения. Контрольные запросы покрывают subset, перестановку,
частичную разводку, свободные каналы, одинаковые установки, активный
конец, цикл, DIRECT_CONNECTION, MODEL_ERROR и INVALID_CANONICAL_DATA.
Регрессия отдельно проверяет срок жизни снимка при параллельном изменении
и ограничивает число SQL и обходов без порога по времени.

## Воспроизведение

В выделенном Compose-проекте `netmap-l1-trace-perf-01` запустить
`test-backend` из checkout базового SHA по `compose.test.yaml`. Скопировать
[скрипт замера](../perf/l1_trace.py) из текущей ветки в
`/app/perf/l1_trace.py` этого контейнера. Скрипт требует изолированную
`netmap_test` с маркером `NETMAP_TEST_DATABASE=1`.

В первом контейнере выполнить:

```sh
python -m perf.l1_trace --seed --cases /tmp/l1-cases.json --output /tmp/l1-before.json --server http://127.0.0.1:8000
python -m perf.l1_trace --seed-probes-from /tmp/l1-cases.json --cases /tmp/l1-probes.json --output /tmp/l1-probes-before.json
```

Скопировать четыре файла JSON из контейнера. Затем в том же проекте
пересобрать и пересоздать только `test-backend` из текущей ветки
(`up -d --build --wait --no-deps test-backend`). Оставить `test-db` запущенной,
чтобы сохранить данные на tmpfs. Вернуть `l1-cases.json` и `l1-probes.json`
в `/tmp` нового контейнера и выполнить:

```sh
python -m perf.l1_trace --cases /tmp/l1-cases.json --output /tmp/l1-after.json --server http://127.0.0.1:8000
python -m perf.l1_trace --cases /tmp/l1-probes.json --output /tmp/l1-probes-after.json
```

В отчётах сравнить `metrics.status` и `artifact` для каждого сценария.
`artifact_sha256` вычисляется по JSON с упорядоченными ключами объектов
и исходным порядком элементов массивов. Тестовый прогон с очисткой БД
можно выполнять после сохранения отчётов.

включает по два Cable на канал, пассивный модуль с точной обратной перестановкой
